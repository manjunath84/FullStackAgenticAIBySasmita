Subgraphs in LangGraph,and a First Look at MCP

Two compositional moves: plug a compiled graph into a parent graph, and pull tools out of every agent into a shared protocol. Same idea, different scope.

LANGGRAPH SUBGRAPHS MCP  ·  JSON-RPC 2.0
A subgraph is a compiled StateGraph used as a node — the state schema is the only contract. MCP is the same move one level up: pull tools out of every agent and put them behind a published protocol so you maintain them in one place.
Scope note. Session 22 covers two distinct topics: LangGraph subgraphs (≈ first 35 minutes), then an intro to MCP (≈ last 20 minutes). Each gets its own threshold concept below. The unifying frame above is real but lightweight — don't read it as a single mechanism.
WHERE WE ARE

Pipeline position

S21 left you with a graph that pauses at interrupt(), persists state via a checkpointer keyed by thread_id, and uses Command(goto=…, update=…) to route between nodes. S22 takes those ingredients and asks one question: what if a "node" is itself a whole graph?

PART A — SUBGRAPHS
§ 01 — WORKED-EXAMPLE OPENER

Predict the output, then read the code

The lecturer's notebook (§3) runs this exact code:

class SharedState(TypedDict):
    foo: str

def subgraph_step(state: SharedState) -> dict:
    return {"foo": "subgraph says hi → " + state["foo"]}

sub_b = StateGraph(SharedState)
sub_b.add_node("inner", subgraph_step)
sub_b.add_edge(START, "inner")
sub_b.add_edge("inner", END)
subgraph_app = sub_b.compile()                # ← compile first

def parent_first(state: SharedState) -> dict:
    return {"foo": "parent: " + state["foo"]}

pb = StateGraph(SharedState)
pb.add_node("parent_1", parent_first)
pb.add_node("embedded_subgraph", subgraph_app)   # ← compiled graph used as a node
pb.add_edge(START, "parent_1")
pb.add_edge("parent_1", "embedded_subgraph")
pb.add_edge("embedded_subgraph", END)

parent_shared = pb.compile()
print(parent_shared.invoke({"foo": "world"}))

Speaker B in the transcript guessed "parent world, subgraph say hi, parent world". The real output is:

{'foo': 'subgraph says hi → parent: world'}
Misconception harvest. You might think the order of the string mirrors the order of execution — parent first, then subgraph. It doesn't. Execution order and string-concatenation order are different axes. parent_first ran first and wrote "parent: world". Then subgraph_step prepended "subgraph says hi → " to that. The final string reads child-first because of how + is wired in subgraph_step, not because the subgraph ran first.
FAILURE TELL — when a subgraph's output "looks reversed," check the concatenation order inside the inner node before you suspect graph topology.
If you change subgraph_step to return {"foo": state["foo"] + " ← subgraph says hi"}, what will parent_shared.invoke({"foo": "world"}) print?
§ 02 — PATTERN A

Subgraph as a node (shared state)

When parent and child use the same state keys, you do nothing clever. Compile the subgraph, then pass it to add_node the same way you'd pass a function:

builder.add_node("embedded_subgraph", subgraph_app)

LangGraph reads the inputs the subgraph needs straight from the parent's state and writes its outputs back. No wrapper, no mapping.

JAVA / SPRING BRIDGE

This is the move where you register a @Bean that exposes a process() method into a parent ApplicationContext. The compiled StateGraph is the bean; add_node("embedded_subgraph", subgraph_app) is @Bean-style registration. The parent doesn't know whether the node is a function, an LLM call, or a multi-node graph — it sees only the state-schema contract.

The key requirement is that the subgraph's TypedDict and the parent's TypedDict share the keys the subgraph reads and writes. If they don't, Pattern A won't work and you fall to Pattern B.

Why does the subgraph not need a wrapper function in this pattern?
§ 03 — PATTERN B

Subgraph invoked inside a node (different states)

When the schemas don't match, you put a node in the parent whose entire job is to invoke the subgraph with mapped inputs and translate the response back:

class SubState(TypedDict):
    bar: str

def sub_inner(state: SubState) -> dict:
    return {"bar": state["bar"] + " [processed in subgraph]"}

sub_only = StateGraph(SubState)
sub_only.add_node("only", sub_inner)
sub_only.add_edge(START, "only")
sub_only.add_edge("only", END)
sub_compiled = sub_only.compile()

class ParentOnlyState(TypedDict):
    foo: str

def bridge(state: ParentOnlyState) -> dict:
    out = sub_compiled.invoke({"bar": state["foo"]})   # ← parent.foo → sub.bar
    return {"foo": out["bar"]}                          # ← sub.bar → parent.foo

wb = StateGraph(ParentOnlyState)
wb.add_node("call_sub", bridge)
wb.add_edge(START, "call_sub")
wb.add_edge("call_sub", END)
wrapped_app = wb.compile()
print(wrapped_app.invoke({"foo": "start-value"}))
# {'foo': 'start-value [processed in subgraph]'}
JAVA / SPRING BRIDGE

This is the layered-service pattern — OrderService calls PaymentService, but OrderService doesn't pass its own DTO across; it constructs a PaymentRequest, calls paymentService.process(request), and maps the PaymentResponse back into its own domain. Subgraph-inside-node is the same anti-corruption layer, written explicitly because Python doesn't have a stricter DTO convention.

The third case — partial overlap

The notebook shows only the two extremes (fully shared SharedState, fully disjoint ParentOnlyState / SubState). In practice you'll also see partial overlap — parent and child share some state keys and have their own private ones. LangGraph handles this by reading/writing only the shared channels automatically; you map the rest yourself in a wrapper. The lecturer alluded to this when he said "there should be some common element to how you can kind of join these two."

§ 04 — HONEST DISANALOGY

A subgraph is not a thread

The lecturer says early on, "the subgraph can be an independent module. So when the main graph is executing, subgraph also can execute parallelly." Later he walks this back: "you cannot actually do parallel execution, but concurrent execution you can do based on async."

The walkback is the right answer. Pinning it down: the subgraph wrapper itself does not parallelize anything. A subgraph used as a single node still executes in turn when the graph reaches that edge. You get parallelism in LangGraph two ways:

  1. Graph topology — fan out from one node to several nodes (which may themselves be subgraphs) using multiple outgoing edges; the runtime executes them in parallel for that step. The Send API and conditional fan-out are the usual moves.
  2. Async invocation — define your nodes with async def and call await graph.ainvoke(...); the runtime can interleave I/O-bound nodes (LLM calls, HTTP requests) concurrently.
HONEST DISANALOGY — NOT A THREAD

Wrapping a slow operation in a subgraph is the LangGraph equivalent of moving slow code into its own class — it organizes, it doesn't speed anything up. Concurrency in Java/Spring needs CompletableFuture, @Async, or a reactor; in LangGraph it needs fan-out edges or async nodes. Encapsulation alone is not concurrency.

FAILURE TELL — when the cohort says "I put the slow tool in a subgraph and it's still slow," that's this confusion.
Name two ways to actually get two LLM calls to overlap in LangGraph.
§ 05 — ESCAPE HATCH

Where subgraphs and Command.PARENT meet

S21 introduced Command(goto=…, update=…) as a way to route from inside a node without writing a conditional edge. With subgraphs, Command gains one more knob: graph=Command.PARENT.

When a subgraph node returns Command(update={…}, goto="some_parent_node", graph=Command.PARENT), the runtime updates the parent's state and jumps to a node in the parent graph — skipping the rest of the subgraph entirely. That's how you escape a subgraph mid-run from the inside (e.g., "if validation fails inside the sub, send control back to the supervisor"). It's the subgraph version of "raise to the caller."

Mechanism, not magic: it requires that the shared state key has a reducer (e.g., Annotated[str, operator.add]) so the parent knows how to merge the subgraph's update. Without the reducer LangGraph won't know whether to overwrite or accumulate.

Why does Command.PARENT require reducers on shared keys?
§ 06 — WORKED USE CASE

A travel-itinerary supervisor

This is the lecturer's example, made concrete. You're building a travel agent: the user gives a destination, a date range, and a party size. The supervisor needs to (i) search flights, (ii) book hotels, (iii) generate an itinerary. Each is a small graph:

  • Flight subgraph — its own internal ReAct loop (search → filter → score), shared flight_options: list[dict] with the parent.
  • Hotel subgraph — same shape, shared hotel_options: list[dict]; depends on flight_options[0].arrival_time so it runs after the flight subgraph, not in parallel.
  • Itinerary subgraph — Reflection pattern (draft → critique → revise), reads the booked flights and hotels, writes itinerary: str.

In the parent supervisor graph each of these is a node — add_node("book_flights", flights_compiled) — wired with sequential edges where dependency exists, and conditional edges where the supervisor decides. The supervisor's whole job is orchestration; each subgraph owns its domain. This is the pattern multi-agent systems formalize: a thin top-level graph composed of fat domain graphs.

PART B — A FIRST LOOK AT MCP
§ 07 — THE PROBLEM

Why a protocol, not a library

You write a web_search tool with @tool and bind_tools(...) in your agent. So does the team across the hall. So does every other agent project in the company. Now: a search API endpoint changes. How many codebases need a patch? One per project. Times the security review. Times the on-call who'll get paged at 2 a.m. when one of them lags.

JAVA / SPRING BRIDGE

This is exactly the JAR-versus-microservice debate. A common-utilities JAR sounds great until you have 200 services pinning 17 different versions of it. The fix is to extract the thing behind a published API and let the calling code be a thin client. MCP is that move, scoped to tools an LLM can call.

The lecturer's USB-port analogy is the canonical one Anthropic uses too: before MCP, every "agent ↔ tool" pair was a custom cable; MCP is the standard port. The point isn't capability — the model isn't smarter with MCP — it's maintainability and security at scale.

CALIBRATION — WHEN MCP DOESN'T EARN ITS KEEP

MCP pays off at organization scale. For a single project with 20–30 tools, MCP is over-engineering. The lecturer is explicit: "if you have small project… don't go for MCP."

Reach for it when tools are shared across teams, when security review needs a single chokepoint, or when the tool list is large enough that an LLM's "discover the right tool from the bound list" step starts hallucinating across similarly-named tools.

§ 08 — WHAT MCP IS

What MCP is, precisely

MCP (Model Context Protocol) is an open protocol — published by Anthropic in November 2024 — that standardizes how an LLM application (the host) connects to external context and tools.

The spec defines two layers:

  • Data layer — a JSON-RPC 2.0 protocol that defines the primitives (tools, resources, prompts, notifications), lifecycle messages, and authorization. This is the contract every server and client must implement.
  • Transport layer — how the bytes move. Two standard transports: stdio (client launches the server as a subprocess; JSON-RPC messages over stdin/stdout, newline-delimited) and Streamable HTTP (the current HTTP-based transport; the older HTTP+SSE transport is now deprecated but still supported by some clients for compatibility).
Correction. The lecturer described MCP as "a transport-layer protocol, like the 7 layers in networking." That phrasing mixes OSI layers — at the OSI transport layer you have TCP and UDP, not protocols that define methods like tools/list. MCP is closer to an application-layer protocol (built on JSON-RPC) that uses underlying transports. The MCP spec itself names "data layer" (JSON-RPC) and "transport layer" (stdio, Streamable HTTP) as its internal layers. [Source: modelcontextprotocol.org/docs/learn/architecture; modelcontextprotocol.org/specification/latest/basic/transports, retrieved 2026-05-20.]
JAVA / SPRING BRIDGE

Treat MCP like JSON-RPC over stdio or HTTP rather than like a fresh wire format. If you've used Spring Remoting or a JSON-RPC client before, the mental model carries over: methods, params, errors, ids, notifications.

§ 09 — THE THREE PRIMITIVES

Tools, resources, prompts — who controls each

The transcript collapses this into "tools are auto-discoverable, resources need hard coding." The spec is more precise — the distinction is who drives the call:

PrimitiveControlled byTypical useSpec method
ToolsModel (LLM decides when to call)API calls, file writes, DB mutations — actions with effectstools/list, tools/call
ResourcesApplication (host injects as context)File contents, git history, ticket payloads — read-only contextresources/list, resources/read
PromptsUser (explicit invocation)Slash commands, menu options (/review-code)prompts/list, prompts/get
Correction. "Tools are auto-discoverable; resources are like a repository, you need to hard code" is a clumsy phrasing of the table above. Tools aren't auto-discovered by magic — the host calls tools/list and exposes the result to the model; the model then decides whether to use them. Resources aren't "hard-coded" — the application chooses what to attach. The contrast that matters is who decides to invoke, not whether the call appears in code. [Source: modelcontextprotocol.org/specification/latest/server, retrieved 2026-05-20.]

A fourth concept, notifications, lets servers push state updates ("the file you read just changed") to the host.

SAFETY NOTE — "MODEL-CONTROLLED" ≠ UNSUPERVISED

The MCP spec is explicit that tool implementations should keep a human in the loop with the ability to deny a tool call before it executes. Hosts like Claude Code and Cursor show a confirmation dialog by default; you can disable it, but the spec assumes you start with it on. [Source: modelcontextprotocol.org/specification/latest/server/tools, retrieved 2026-05-20.]

Your team needs the assistant to (a) read a Confluence page when the user runs /load-runbook, (b) attach the last three on-call incidents automatically to every conversation in the on-call channel, and (c) be able to delete stale incident tickets when the user asks. Map each to the right primitive.
§ 10 — ARCHITECTURE

Host, client, server

  • Host — the LLM application the user interacts with (Claude Code, Cursor, VS Code with an MCP-enabled extension, your own Gradio app). The host runs the LLM and manages conversations.
  • Client — the per-server adapter inside the host that speaks MCP. One client per connected server. (If your host talks to GitHub MCP and a private internal MCP, that's two clients.)
  • Server — the process exposing tools, resources, and prompts. Can be local (stdio, launched as a subprocess) or remote (HTTP). One server can group dozens of related tools.

When the user types something:

  1. Host gathers user input plus any application-controlled resources attached to the conversation.
  2. Host sends that context to the LLM, along with the list of tools the LLM may call.
  3. If the LLM emits a tool call, the host routes it to the correct client, which RPCs the server, gets a result, and returns it to the LLM.
  4. The LLM uses the result to continue generating, possibly calling more tools.
FAILURE TELL — when the assistant says it called a tool but you see no server-side log, check the client→server mapping. The host may have decided the tool wasn't available (server died, transport disconnected, capability not advertised) and the model is hallucinating the call because the tool name is in its training prior.
In the host/client/server picture, where does authentication and authorization live — on the model, in the client, or on the server?
§ 11 — MINIMAL SHAPE

The lecturer's example, made spec-faithful

# server.py — using the official Python MCP SDK
from mcp.server.fastmcp import FastMCP

mcp = FastMCP("demo-server")

@mcp.tool()
def add(a: int, b: int) -> int:
    """Add two numbers."""
    return a + b

@mcp.tool()
def greet(name: str) -> str:
    """Greet someone by name."""
    return f"Hello, {name}!"

if __name__ == "__main__":
    mcp.run(transport="stdio")
# client.py — listing and calling tools
from mcp import ClientSession, StdioServerParameters
from mcp.client.stdio import stdio_client

async def main():
    params = StdioServerParameters(command="python", args=["server.py"])
    async with stdio_client(params) as (read, write):
        async with ClientSession(read, write) as session:
            await session.initialize()
            tools = await session.list_tools()
            print(tools)
            result = await session.call_tool("add", {"a": 5, "b": 3})
            print(result.content)
Correction. The lecturer's client.list_of_tools is session.list_tools() in the Python SDK (and the JSON-RPC method name is tools/list). Small detail, but the reader will hit it the first time they wire this up.

The shape mirrors the lecturer's slide: the client has no tools defined locally — they all live on the server. Everything routes through session.call_tool(name, args).

Debugging

  1. You added a subgraph via add_node and the parent compiles but invocations raise KeyError: 'foo' when the subgraph runs. Most likely cause?
  2. Your MCP-backed agent "says" it called delete_ticket(12) but no log appears on the server. The conversation continued as if it succeeded. What's happening, and where do you look first?
  3. The lecturer's example printed {'foo': 'subgraph says hi → parent: world'}. A cohort member says "that can't be right, parent_first ran first, so it should be 'parent: world subgraph says hi'." In one sentence, why is the cohort member wrong?
Show answers
  1. The state schema (the TypedDict).
  2. Model Context Protocol; its data layer is JSON-RPC 2.0.
  3. Prompts (e.g., slash commands).
  4. Pattern A (subgraph-as-node). The shared messages key means LangGraph reads and writes it automatically — no wrapper needed.
  5. Pattern B. The bridge: out = translate_sub.invoke({"source_text": state["user_request"]}); return {"agent_reply": out["translated_text"]}.
  6. No. 35 tools in one project is below the MCP-payoff line. Keep @tool + bind_tools until cross-project sharing becomes the bottleneck.
  7. One MCP server (or a small number grouped by domain), and 80 clients. The point of MCP is one place to maintain the tool, not 80.
  8. The subgraph's state schema declares a key the parent's state doesn't have, and you're using Pattern A. Either align the schemas or switch to Pattern B with explicit mapping.
  9. The model is hallucinating a tool call — most likely the MCP client lost its connection to the server (server crashed, transport died, capability not advertised) and the model emitted a call that looks plausible from its training prior. Check the client logs for disconnect/reconnect events and the host's tool-list at the moment of the call.
  10. The order of string concatenation in subgraph_step is independent of the order of node execution. parent_first did run first; subgraph_step then prepended its text to the result.
LOOSE ENDS & ASIDES

Things worth keeping but not first-class

  • Multiple subgraphs in one node. The lecturer notes you can invoke several subgraphs from inside a single node, fanning logic together. Fine but harder to debug — prefer one subgraph per node and let the parent graph orchestrate.
  • Command vs add_edge style. The lecturer prefers add_edge for clarity. The cohort will see both in the wild. They're equivalent in expressive power; pick one per codebase and stick with it.
  • API-key leaks in source notebooks. Two of the LangGraph tutorial files in SasmitaCourse/Langgraph/ ship with hard-coded OpenAI keys. Rotate the keys, then move them to os.environ.get("OPENAI_API_KEY") and a .env file outside source control. The README repeats this with file paths and line numbers.

Glossary

StateGraph
LangGraph's builder class for stateful graphs. You add nodes and edges, then call .compile() to get an executable graph.
compile()
Turns a StateGraph builder into an executable, immutable graph object. Required before using it as a node in a parent graph.
add_node(name, target)
Registers a node. target can be a function, async function, or another compiled StateGraph — that's what makes Pattern A work.
add_edge(src, dst)
Static edge from src to dst. Unconditional.
Subgraph
A compiled StateGraph used as a node inside another graph. The unit of composition.
Parent graph
The graph that contains a subgraph as one of its nodes. Topological, not inheritance.
Shared state
When parent and subgraph use the same TypedDict on the keys the subgraph touches. Enables Pattern A.
State mapping
Manually translating parent state keys to subgraph state keys (and back) in a wrapper. Required for Pattern B.
Command
A node return value bundling a state update with a routing decision (goto). graph=Command.PARENT routes into the parent graph.
interrupt()
Pauses graph execution at a node so a human (or another process) can review and resume with Command(resume=…). Introduced in S21.
MCP
Model Context Protocol. An open protocol (Anthropic, Nov 2024) for connecting LLM hosts to external tools, resources, and prompts via JSON-RPC over standardized transports.
MCP server
A process exposing tools, resources, and prompts per the MCP spec. Local (stdio) or remote (Streamable HTTP).
MCP client
The per-server adapter inside a host that speaks MCP to one server. One client per connected server.
Host
The LLM-running application the user interacts with (Claude Code, Cursor, your own app). Hosts contain clients.
Transport
How MCP messages move between client and server. Standard transports: stdio and Streamable HTTP. Older HTTP+SSE deprecated but still seen.
JSON-RPC
A simple RPC protocol over JSON (methods, params, ids, errors). MCP's data layer is JSON-RPC 2.0.
Tools
MCP's model-controlled primitive. The LLM decides when to call. tools/list, tools/call.
Resources
MCP's application-controlled primitive. The host attaches them as context.
Prompts
MCP's user-controlled primitive. Slash commands, menu options, explicit user invocations.
@tool
LangChain decorator that registers a function as an LLM-callable tool. Pre-MCP, all tools live this way inside each project.
bind_tools
Method on a LangChain LLM that attaches a list of @tool-decorated functions for the model to choose from.
Auto-discovery
Loose term; in MCP, the host calls tools/list to enumerate available tools before exposing them to the model. The model discovers them when shown the list; the host does the listing.
Async / ainvoke
Async variants of LangGraph's invocation API. Required (with async def nodes) to interleave I/O-bound operations.
Concurrent vs parallel
Concurrent = multiple ops in flight at once (one CPU, lots of await). Parallel = literally simultaneous on multiple CPUs/processes.
