Vanilla RAG retrieves chunks by similarity. Some answers don't live in a chunk — they live in the relationships between chunks. That's the problem GraphRAG addresses.

CHAPTER 01

Why basic RAG isn't enough

Plain RAG (Sessions 12–14) retrieves chunks by vector similarity, optionally re-ranks them with a cross-encoder, and stuffs the top few into the prompt. That works well when the corpus is reasonably uniform prose, the answer to a typical question sits in one chunk (or a few nearby ones), and "similar" is a useful proxy for "relevant."

It starts to break when:

  1. The answer is scattered across many sections — a 2,000-page operations manual, a policy book, a knowledge base where context A points at context B which references context C.
  2. The answer is reasoning-based, not lexically present. The chunks containing the building blocks may not be similar to the question on their own.
  3. The corpus has rich, structured cross-references — SOPs that say "Step 2: see the eligibility-check URL," or a regulation that references another regulation.

In these cases vector retrieval brings back chunks that look topical but don't combine to the answer, and reranking can't rescue what was never retrieved.

HONEST FRAMING

The lecturer said vanilla RAG is "mostly for simple/scientific documents." Softening that: vanilla RAG works on plenty of enterprise prose. What it struggles with is multi-hop retrieval — answers assembled from chunks that aren't individually a good match for the question. GraphRAG targets that gap specifically.

The fix is to give the retriever a second view of the corpus, one that captures relationships between entities: a graph. That's GraphRAG.

TERM ORIGIN

"GraphRAG" as a named approach is most associated with Microsoft Research — Edge et al., From Local to Global: A Graph RAG Approach to Query-Focused Summarization, arXiv:2404.16130 (2024). It is not "the next version of RAG"; it's a parallel/complementary retrieval channel.

CHAPTER 02

The graph database landscape — and why Neo4j

A graph database stores data as nodes (entities) and relationships (typed edges between entities). Both nodes and relationships can carry properties (key-value pairs). That's the entire model.

DatabaseTypeNotes
Neo4jNative graph DBMarket leader. Cypher query language. Used for the course.
TigerGraphNative graph DBPerformance-oriented, GSQL query language.
Azure Cosmos DB (Gremlin API)Multi-modelHas a managed graph offering via Gremlin (not Cypher). The lecturer called it "not native"; more precisely, it stores graph data on a multi-model engine rather than a graph-native storage layer.

The course uses Neo4j because (a) it has the largest community and tooling ecosystem, (b) it integrates cleanly with LangChain via langchain-neo4j, and (c) the lecturer's team uses it in production for fraud-detection work.

JAVA/SPRING BRIDGE

Neo4j ↔ a Spring Data project: there is a real spring-data-neo4j library. Java entities become nodes via @Node; outgoing edges become fields annotated @Relationship(type = "...", direction = OUTGOING). If you've used Spring Data JPA, the mental model transfers — repositories, derived queries, the whole CrudRepository<T, ID> pattern is present. The unfamiliar part is the query language, not the object mapping.

2.1 Why a graph helps beyond RAG

The lecturer's wider point: graph databases earn their keep in domains where relationships are the data. A few production patterns:

  • Fraud detection. Insurance / banking / claims: identify suspicious networks — a doctor who refers to a hospital that refers to a lab that bills the same insurer that the doctor's spouse owns. The fraud signal lives in the connection topology, not in any single record.
  • Recommendation. "Friends of friends" (Facebook), "people who took this route also took…" (Uber/Ola), product recommendations from co-purchase graphs.
  • Agent context layer. Storing an organization's domain knowledge (entities, their relationships, their attributes) in a graph that an agent can query at runtime. The lecturer flagged this as most important — "we're moving from prompt engineering to context engineering" — RAG just happens to be one application of it.

WHAT THE COURSE USES

For learning and POCs: Neo4j Desktop (the free Community-based local app). Same engine as Community, no automated backup, runs at bolt://localhost:7687. When the project graduates to production, swap to Aura (managed) or Enterprise (self-hosted with full features).

3.1 Two things the lecturer warned about

  1. Pick a password you can recover. The Desktop UI's password-reset flow is not obvious; the lecturer lost ~15 minutes trying to recover his and ended up resetting from the command line. This is why his live demo in this session didn't run.
  2. "Desktop / Community is local only." The free editions do not expose a shareable hosted URL out of the box. To let teammates query the same instance you either (a) host Neo4j on an internal Linux server everyone can reach over bolt://, or (b) use Aura, which exposes a hosted URL by design.
CHAPTER 04

Connecting from Python via LangChain

The end-to-end three-line connection. Package install once:

pip install langchain-neo4j neo4j python-dotenv langchain-community

Then in code:

import os
from dotenv import load_dotenv
from langchain_neo4j import Neo4jGraph

NEO4J_URI      = "bolt://localhost:7687"
NEO4J_USERNAME = "neo4j"
NEO4J_PASSWORD = "<your password>"

kg = Neo4jGraph(
    url=NEO4J_URI,
    username=NEO4J_USERNAME,
    password=NEO4J_PASSWORD,
    database="demo",
)

kg.refresh_schema()
print("Connection established and schema refreshed.")

A few notes worth pinning down:

  • Neo4jGraph is in langchain-neo4j, a separate package from langchain-community. The older langchain_community.graphs.Neo4jGraph import path is deprecated; use from langchain_neo4j import Neo4jGraph.
  • bolt:// is Neo4j's binary client protocol on port 7687. For a hosted Aura instance the URL becomes neo4j+s://<id>.databases.neo4j.io (TLS).
  • If database= is omitted, the driver connects to the default database (named neo4j in a fresh install). Community edition supports one user database plus the system DB.

Executing a Cypher query is then literally one method call:

result = kg.query("MATCH (n) RETURN count(n) AS numberOfNodes")
print(result)   # [{'numberOfNodes': 7}]

.query() returns a list of dicts — one dict per row, keyed by the RETURN aliases.

JAVA/SPRING BRIDGE

Neo4jGraph plays the role of JdbcTemplate or EntityManager: a connection-bearing object you ask to execute a query string. The result list of dicts is the Cypher analogue of List<Map<String, Object>> from a JdbcTemplate.queryForList(...) call.

CHAPTER 05

Cypher in one session — the actual query language

Cypher is Neo4j's declarative query language. Same role as SQL, different shape because the data is a graph. Two design ideas drive the syntax:

  1. Patterns look like ASCII drawings of subgraphs. A node is (variable:Label {prop: value}). A relationship is -[variable:TYPE {prop: value}]->. You match by writing what the subgraph should look like.
  2. There is no fixed schema. Nodes and relationships carry whatever properties you give them; two nodes with the same label can have different property sets.

The full surface is large (functions, subqueries, list comprehensions, path algorithms, vector indexes since Neo4j 5.11). This session covers the minimum required to read what a code-generating agent emits.

5.1 The two entities — node and relationship

  • Node — an entity. Has zero or more labels (think Java interface implementations — a node can carry several at once). Has zero or more properties (a Map<String, Object>).
  • Relationship — a typed, directed edge between two nodes. Has exactly one type (the "label" of the relationship). Has zero or more properties of its own.
WORKED EXAMPLE RECONSIDERED

The lecturer said the sentence "Shivaji is king of Maratha" maps to "3 nodes." In Cypher that is more naturally 2 nodes and 1 relationship:

(:Person {name: 'Shivaji'})-[:KING_OF]->(:Kingdom {name: 'Maratha'})

Two nodes — Shivaji (label Person) and Maratha (label Kingdom) — connected by a single KING_OF relationship. The verb of the sentence becomes the relationship type, not a third node.

5.2 Creating nodes — CREATE

CREATE (p1:Person {name: 'Alice Johnson', age: 28, city: 'New York'})
CREATE (p2:Person {name: 'Bob Smith',    age: 35, city: 'San Francisco'})
CREATE (p3:Person {name: 'Carol White',  age: 42, city: 'Boston'})
CREATE (p4:Person {name: 'David Brown',  age: 31, city: 'Seattle'})
RETURN 'Created 4 Person nodes' AS result

Parse it as: CREATE (variable:Label {properties}). p1, p2, … are variables local to the query. :Person is the label. {...} is the property map.

A node can carry multiple labels:

CREATE (c1:Company:TechCompany {
    name: 'TechCorp',
    founded: 2010,
    industry: 'Software',
    employees: 500
})
CREATE (c2:Company:TechCompany {
    name: 'DataSolutions',
    founded: 2015,
    industry: 'Data Analytics',
    employees: 150
})
RETURN 'Created 2 Company nodes with multiple labels' AS result

Both c1 and c2 match queries for :Company and :TechCompany. The lecturer's framing: "Microsoft is a tech company and a cloud company" — multiple labels let you say that without picking one.

5.3 Creating relationships — combining MATCH and CREATE

MATCH (p:Person  {name: 'Alice Johnson'}),
      (c:Company {name: 'TechCorp'})
CREATE (p)-[r:WORKS_AT {since: 2020, position: 'Software Engineer'}]->(c)
RETURN p.name + ' works at ' + c.name AS result

Read the pattern from left to right: (p) is the Alice node we just matched; -[r:WORKS_AT {…}]-> is a relationship with type WORKS_AT (one type per edge, mandatory), property map, and direction; (c) is the TechCorp node.

Several CREATEs can be chained with WITH to keep matched variables in scope across stages:

MATCH (p1:Person  {name: 'Bob Smith'}),
      (c:Company {name: 'DataSolutions'})
CREATE (p1)-[:WORKS_AT {since: 2019, position: 'Data Scientist'}]->(c)

WITH p1
MATCH (p2:Person {name: 'Alice Johnson'})
CREATE (p1)-[:KNOWS {since: 2018, relationship: 'Friends'}]->(p2)

RETURN 'Created multiple relationships' AS result

WITH is Cypher's way of saying "carry these variables forward into the next clause." Without it, p1 would no longer be in scope after the first CREATE.

PITFALL — USE MERGE FOR UPSERTS

Plain CREATE always makes a new node, even if one with the same properties already exists. To get "create if missing, update if present" semantics, use MERGE:

MERGE (p:Person {name: 'Alice Johnson'})
ON CREATE SET p.created  = timestamp()
ON MATCH  SET p.lastSeen = timestamp()
RETURN p.name, p.created, p.lastSeen

MERGE matches by the pattern you give it; if it doesn't find one, it creates it. ON CREATE SET runs only on the creation branch, ON MATCH SET only on the match branch. This is the closest Cypher equivalent of SQL's INSERT ... ON DUPLICATE KEY UPDATE / upsert.

5.4 Reading — MATCH + RETURN

MATCH is the analogue of SQL SELECT ... FROM. You give it a pattern; Neo4j returns every subgraph that matches.

MATCH (p:Person)
RETURN p.name AS name, p.age AS age, p.city AS city
ORDER BY p.age
  • MATCH (p:Person) — bind variable p to every node carrying the Person label.
  • RETURN p.name AS name, … — project each result row to the named columns.
  • ORDER BY p.age — ascending sort; DESC for descending.
JAVA/SPRING BRIDGE

A Cypher pattern is structurally closer to a JPA Criteria pattern than to a SQL query: you describe the shape you want, the engine figures out the traversal. There is no FROM clause because the "table" is implicit in the labels you use.

5.5 Filtering — WHERE

MATCH (p:Person)
WHERE p.age > 30
RETURN p.name AS name, p.age AS age

Multiple conditions combine with AND, OR, NOT; IN works on lists:

MATCH (p:Person)
WHERE p.age >= 30
  AND p.city IN ['New York', 'Boston']
RETURN p.name AS name, p.age AS age, p.city AS city

You can filter on relationship properties too, by binding the relationship to a variable:

MATCH (p1:Person)-[k:KNOWS]->(p2:Person)
WHERE k.since < 2020
RETURN p1.name AS person1,
       p2.name AS person2,
       k.since  AS friendsSince

k here is the relationship variable. k.since is one of its properties. The same dot-access works on nodes (p1.name) and relationships (k.since) — Cypher treats them symmetrically.

5.6 Aggregation — COUNT, AVG, MIN, MAX

Aggregation functions live inside RETURN. There is no explicit GROUP BY clause — grouping is implicit: every non-aggregated column in RETURN becomes a group key, and the aggregated columns are computed per group.

Whole-corpus aggregation (no grouping columns):

MATCH (p:Person)
RETURN COUNT(p)    AS totalPeople,
       AVG(p.age)  AS avgAge,
       MIN(p.age)  AS youngest,
       MAX(p.age)  AS oldest

Aggregation grouped by city — note that p.city is the (implicit) group key:

MATCH (p:Person)
RETURN p.city      AS city,
       COUNT(p)    AS peopleCount,
       AVG(p.age)  AS avgAge
ORDER BY peopleCount DESC
CORRECTION

The lecturer used the phrase "GROUP BY" several times. Cypher does not have a GROUP BY keyword; the grouping happens automatically based on which columns in RETURN are aggregated and which aren't. Functionally equivalent to SQL, syntactically different.

5.7 Updating — SET

MATCH (p:Person {name: 'Alice Johnson'})
SET p.age   = 29,
    p.email = 'alice@example.com'
RETURN p.name AS name, p.age AS age, p.email AS email

SET adds new properties or overwrites existing ones. There is no "schema migration" step — adding a property to one node does not require touching the others. This is what the lecturer means by schema-less: properties live on individual nodes, not on a table-wide definition.

5.8 Querying relationships explicitly

MATCH (p:Person)-[r:WORKS_AT]->(c:Company)
RETURN p.name    AS employee,
       r.position AS position,
       c.name    AS company,
       r.since   AS startYear

In SQL terms this is a join — Person and Company are joined via the WORKS_AT relationship. The difference is that the "foreign key" isn't a column in either table; it's an edge stored as a first-class object, and you traverse it by writing it in the pattern.

JAVA/SPRING BRIDGE

SQL JOIN ↔ Cypher pattern traversal. The classical JPA approach to "people and their employers" needs a join table or a @ManyToOne; Cypher just draws the connection in the MATCH clause.

CHAPTER 06

Where this is going — the GraphRAG end-state

The architecture the lecturer sketched at the end (full implementation in Session 16+):

Two retrieval channels feeding one LLM:

  • Vector channel — what Sessions 12–14 built. Captures semantic similarity. Misses multi-hop / relational answers.
  • Graph channel — translate the natural-language question into a Cypher query, run it against the knowledge graph, format the rows as context. Captures explicit relationships. Misses prose that wasn't extracted into the graph.

The LLM sees both. Recall improves because the channels fail differently; precision improves because graph rows are structured, typed, and (importantly) deterministic — given the same query against the same graph, you get the same rows. That's what the lecturer means by "for the LLM, this is gold" — graph rows are much less likely to mislead than a fuzzy vector match.

A FEW ACCURACY NOTES ON THAT PICTURE

A graph doesn't eliminate hallucination. Hallucination comes from the LLM's sampling step, not from retrieval. Graph retrieval reduces the opportunity to hallucinate by giving the model better-grounded context, but the model is still probabilistic. Don't let anyone tell you GraphRAG is "hallucination-free."

Neo4j 5.11+ can store vectors too. Since the August 2023 release, Neo4j has native vector indexes — you can keep both the graph and the embeddings in the same database and run db.index.vector.queryNodes(...). That's the "two-in-one" the lecturer mentioned.

You still need to build the graph. Going from unstructured documents to a graph is the hard part. Two paths (Session 16 will go deeper): (1) LLM-driven extraction — LangChain ships LLMGraphTransformer (in langchain-experimental) which prompts an LLM to extract (node, relationship, node) triples from each chunk. Quality is highly LLM-dependent. (2) Schema-first extraction — if your documents follow a known structure (insurance policies, financial reports, SOP manuals), define an explicit schema and a deterministic extractor. Slower to build, much more reliable.

CHAPTER 07

Recap

The Session 15 takeaways:

  1. Vanilla RAG struggles with multi-hop and relationship-shaped questions. A graph view of the corpus gives the retriever a second channel that handles exactly those cases.
  2. A graph database stores two entities — nodes and relationships — both of which carry labels/types and arbitrary property maps. There is no fixed schema; you add fields per node as needed.
  3. Cypher is Neo4j's query language. It is pattern-based: you draw what the subgraph should look like — (:Label)-[:TYPE]->(:Label) — and the engine finds the matches. CREATE, MATCH, WHERE, RETURN, ORDER BY, SET, and aggregation functions are the core surface; grouping is implicit.
  4. LangChain talks to Neo4j via the langchain-neo4j package. Neo4jGraph(...) is the connection; kg.query("…") runs Cypher and returns a list of dicts.
  5. For learning, use Neo4j Desktop (free, Community-based). For production, Aura (managed) or Enterprise (self-hosted with full features). Pick a password you can recover.
  6. GraphRAG = vector channel + graph channel → LLM. The graph channel needs you to build the graph first; Session 16 covers how.
GLOSSARY

Glossary

Node
A graph-database entity. Carries zero or more labels and zero or more properties.
Relationship (edge)
A typed, directed connection between two nodes. Carries exactly one type and zero or more properties.
Label
A category marker on a node (e.g. :Person, :Company). A node may have several.
Type
The single category marker on a relationship (e.g. :WORKS_AT). Always exactly one per relationship.
Property
A key-value pair on a node or relationship. The value can be a primitive, list, or map. Schema-less by default.
Cypher
Neo4j's declarative query language. Pattern-based syntax; clauses include CREATE, MERGE, MATCH, WHERE, RETURN, ORDER BY, SET, WITH, plus aggregation functions.
MERGE
"Match if it exists, else create." The upsert primitive. Pair with ON CREATE SET / ON MATCH SET for branch-specific updates.
WITH
Pipes results from one clause to the next, controlling which variables stay in scope.
Bolt
Neo4j's binary client/server protocol. Default port 7687. URL form bolt://host:port (or neo4j+s://... for Aura with TLS).
Neo4jGraph
The LangChain class (in langchain-neo4j) wrapping a Neo4j connection. Methods: .query(cypher), .refresh_schema(), .schema.
Neo4j Community
Open-source GPLv3 edition. Single user database, no role-based security, documented ceiling of 34B nodes / 34B rels / 68B properties.
Neo4j Aura
Neo4j-managed cloud service. Tiers: Free (small caps, currently ~200K nodes / 400K rels), Professional, Business Critical. Automated backups; hosted UI included.
Neo4j Enterprise
Commercial license. Unlimited graph size, multiple databases, RBAC, advanced constraints. Self-hosted.
Neo4j Desktop
Free local installer based on Community. Same engine, no automated backup, no hosted URL.
GraphRAG
Retrieval-augmented generation that runs both a vector retriever and a graph retriever, feeding both into the LLM context. The named approach is most associated with Edge et al., Microsoft Research, From Local to Global: A Graph RAG Approach to Query-Focused Summarization, arXiv:2404.16130 (2024).
Schema-less
Property keys are stored per node/relationship, not on a global table definition. Adding a property to one node does not require touching the others (or any kind of migration).
