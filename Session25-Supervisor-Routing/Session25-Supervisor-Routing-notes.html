THE THRESHOLD CONCEPT

The supervisor is an LLM call that returns one structured answer: which worker to call next. That decision is only as good as the worker descriptions you put in the supervisor’s system prompt — and MLflow tracing is what makes the gap between “the supervisor should pick X” and “the supervisor actually picked X” visible. Everything in this session — the math node firing three times, the Neo4j Q&A, the REST API integration — orbits that one idea.

What we built in Session 24, briefly recapped

      +-----------+--------------+-------------+-----------+
                                              v
                                      +--------------+
                                      | final_answer | --> END
                                      +--------------+

State carried between nodes (a TypedDict extending ChatAgentState):

class AgentState(ChatAgentState):
    next_node: str          # the supervisor's routing decision
    iteration_count: int    # custom cap to short-circuit if supervisor flaps

The whole graph is compiled with workflow.compile() and then wrapped in LangGraphChatAgent(multi_agent) — the MLflow ChatAgent subclass whose predict() we’ll call. See §04 for the wrapper; see Session 24 for why we need it.

THE SUPERVISOR IS JUST AN LLM CALL

Despite the architectural diagram, the supervisor is not a magic component. It’s llm.with_structured_output(NextNode) where NextNode is a Pydantic model whose only field is Literal["FINISH", "Genie", "Coder", "Weather"]. The system prompt lists the workers with their descriptions, and the LLM picks one. Whatever the LLM picks, that’s what runs next. The supervisor’s quality is bounded by (a) the descriptions you write and (b) the LLM you point it at. Both knobs matter.

§ 02 — DEMO 1: A QUESTION GENIE CAN ANSWER

Clean route, five spans

from agent import AGENT     # the LangGraphChatAgent built in agent.py

input_example = {
    "messages": [
        {"role": "user", "content": "What is the total population in Afghanistan?"}
    ]
}
AGENT.predict(input_example)

What happens, step by step:

  1. AGENT.predict() translates the dict into ChatAgentMessage objects and calls multi_agent.stream(...) underneath.
  2. workflow.set_entry_point("supervisor") — the supervisor runs first. It runs supervisor_chain.invoke(state), which is preprocessor | llm.with_structured_output(NextNode). The LLM, given the worker descriptions in the system prompt and the user message in the chat history, returns NextNode(next_node="Genie").
  3. The supervisor node returns {"iteration_count": 1, "next_node": "Genie"}. The conditional edge maps "Genie" to the genie_node function.
  4. The Genie node invokes the GenieAgent (which hits Databricks’ Genie REST API under the hood — see §06), receives a markdown reply with the SQL query, the reasoning, and the answer rows.
  5. The workflow.add_edge("Genie", "supervisor") edge sends control back to the supervisor.
  6. Supervisor re-runs. This time the chat history includes Genie’s answer. The LLM sees there’s already an answer and returns NextNode(next_node="FINISH").
  7. The conditional edge maps "FINISH" to final_answer, which composes a clean response and routes to END.

The MLflow trace for this run shows exactly five spans: supervisor → Genie → supervisor → final_answer → END. The user gets one well-formed answer.

JAVA / SPRING BRIDGE

If you’ve worked with Spring Integration or Camel routing slips, the supervisor pattern will look familiar. Each worker is an integration endpoint; the supervisor is a content-based router that reads the latest message in the channel and dispatches to one of N downstream endpoints. The difference is that a Camel router is deterministic (XPath / regex / predicate); the LangGraph supervisor is an LLM call with structured output. Same routing topology, stochastic decision function.

§ 03 — DEMO 2: THE 3-CALL INFINITE LOOP

Same code. Different question. Six spans, three Coder calls.

input_example = {"messages": [{"role": "user", "content": "what is 5 + 5"}]}
AGENT.predict(input_example)

What he expected: supervisor → Coder → supervisor → FINISH → final_answer → END — one Coder call.

What MLflow trace actually showed: the supervisor routed to Coder three times in a row before finally returning FINISH:

iteration count 1   <class 'str'> Coder
iteration count 2   <class 'str'> Coder
iteration count 3   <class 'str'> Coder

Sasmita’s on-air reaction: “why it is calling 3 times? It should call 1 time. But yeah, this is where you can add some more logic.”

(a) The MAX_ITERATIONS = 3 was the floor that saved the run

MAX_ITERATIONS = 3

def supervisor_agent(state):
    count = state.get("iteration_count", 0) + 1
    if count > MAX_ITERATIONS:
        return {"next_node": "FINISH"}
    # ... otherwise run the LLM ...

The third hit of the supervisor would have routed to Coder again if not for the count > MAX_ITERATIONS short-circuit. Without that, the trace could have looped indefinitely (or until LangGraph’s built-in recursion_limit kill-switch fired — see §05).

(b) The cause is the supervisor’s system prompt + worker descriptions

The actual prompt in the notebook:

formatted_descriptions = "\n".join(
    f"- {name}: {desc}" for name, desc in worker_descriptions.items()
)
system_prompt = (
    f"Decide between routing between the following workers "
    f"or ending the conversation if an answer is provided. "
    f"\n{formatted_descriptions}"
)

Two problems:

  1. The Coder’s description is “specialises in solving programming challenges, generating code snippets, debugging issues, and explaining complex coding concepts.” Nothing in there discourages routing 5 + 5 to it. The LLM read the description, saw “programming/coding,” concluded “yes, arithmetic is code-ish,” and routed there. Fair.
  2. No instruction to inspect the existing chat history. When the supervisor sees the Coder’s response, it has to re-evaluate whether the answer is sufficient. With no instruction to do so, the LLM hedges and routes to Coder again “just to be safe.” That’s the loop.

(c) The fix is the prompt, not the cap

MAX_ITERATIONS = 3 is a safety net, not a fix. A useful supervisor prompt would say something like:

Decide whether to route to a worker, OR end the conversation by returning FINISH.

If the latest message in the conversation already contains a clear answer to the
user's original question, return FINISH. Otherwise route to exactly one worker
whose description below best matches the question.

Workers:
- Genie: queries structured business data (NYC taxi trips, populations, sales).
        ONLY route here if the question is about stored tabular data.
- Coder: writes and debugs Python code. ONLY route here for programming tasks,
        NOT for arithmetic that the LLM can answer directly.
- Weather: looks up current weather for a named location. ONLY route here for
          weather queries.

With that prompt, the supervisor routes 5 + 5 to FINISH directly (the LLM answers from its own training; no worker call needed). The trace collapses to two spans, not six.

THE SINGLE MOST TEACHABLE LINE IN THE LECTURE

“If the prompt is not very accurate, it can do multiple times iteration and then come to the end. And this problem is called infinite loop. It may happen sometimes in real time.” That’s the headline lesson of Session 25. The supervisor is an LLM; the LLM does what its system prompt tells it to do; vague prompts produce flapping routes; tight prompts don’t. Spend your time writing worker descriptions, not raising recursion caps.

§ 04 — THE CHATAGENT WRAPPER

What Sasmita actually instantiated

The PDF cell that lands the deployable artifact:

import mlflow
from mlflow.pyfunc import ChatAgent
from mlflow.types.agent import (
    ChatAgentChunk, ChatAgentMessage, ChatAgentResponse, ChatContext,
)
from mlflow.langchain.chat_agent_langgraph import ChatAgentState

class LangGraphChatAgent(ChatAgent):
    def __init__(self, agent: CompiledStateGraph):
        self.agent = agent

    def predict(
        self,
        messages: list[ChatAgentMessage],
        context: Optional[ChatContext] = None,
        custom_inputs: Optional[dict[str, Any]] = None,
    ) -> ChatAgentResponse:
        request = {"messages": [m.model_dump_compat(exclude_none=True) for m in messages]}
        out = []
        for event in self.agent.stream(request, stream_mode="updates"):
            for node_data in event.values():
                out.extend(ChatAgentMessage(**msg) for msg in node_data.get("messages", []))
        return ChatAgentResponse(messages=out)

    def predict_stream(self, messages, context=None, custom_inputs=None):
        request = {"messages": [m.model_dump_compat(exclude_none=True) for m in messages]}
        for event in self.agent.stream(request, stream_mode="updates"):
            for node_data in event.values():
                yield from (ChatAgentChunk(**{"delta": msg})
                            for msg in node_data.get("messages", []))

mlflow.langchain.autolog()
AGENT = LangGraphChatAgent(multi_agent)
mlflow.models.set_model(AGENT)

Three things to internalize:

  1. ChatAgent is an MLflow interface, not a LangChain one. It lives in mlflow.pyfunc.ChatAgent. It’s the standard MLflow “I am an LLM agent that takes messages and returns messages” contract. Anything that implements it can be logged with mlflow.pyfunc.log_model(...) and deployed on Mosaic AI Model Serving.
  2. predict() returns a ChatAgentResponse; predict_stream() yields ChatAgentChunks. The predict_stream form enables Server-Sent Events at the deployment surface — your front-end gets tokens as they’re generated, not after the whole graph finishes.
  3. mlflow.langchain.autolog() is the one-liner that turns on MLflow Tracing for everything inside the wrapper. It hooks into LangChain’s callback system; every RunnableLambda, every llm.invoke, every node in the graph, every Genie REST call gets its own span. The MLflow UI then renders the full waterfall — which is how we saw the three Coder calls in §03.
HEADS-UP: ResponsesAgent IS THE NEW RECOMMENDED INTERFACE FROM MLFLOW 3.0

The PDF notebook uses ChatAgent, which was the recommendation when it was written. Since MLflow 3.0.0, Databricks recommends ResponsesAgent for new agents (mlflow.pyfunc.ResponsesAgent). The two are similar in spirit but ResponsesAgent aligns with OpenAI’s newer Responses API rather than the legacy ChatCompletion shape. ChatAgent is still supported and shipping; you don’t have to migrate today. New code should pick ResponsesAgent.

JAVA / SPRING BRIDGE

ChatAgent is a @RestController-like contract: it defines the public method signatures (predict, predict_stream) and the request/response DTOs. Mosaic AI Model Serving is the container that hosts it. The LangGraph compiled graph is the business logic — a service class injected into the controller. Same separation of concerns: API shape upstairs, orchestration downstairs.

§ 05 — LANGGRAPH’s BUILT-IN SAFETY NET

recursion_limit — the floor under your floor

MAX_ITERATIONS = 3 in §03 was a manual counter Sasmita put in his supervisor function. LangGraph itself has a separate, deeper safety net that runs underneath your application logic.

# Per-invocation override:
AGENT.predict(input_example, config={"recursion_limit": 50})
# or directly on the compiled graph:
multi_agent.invoke(input_example, config={"recursion_limit": 50})
  1. The default is 25. Each “step” the graph executes counts. If the supervisor flaps 13 times between two workers (26 steps), LangGraph stops with GraphRecursionError.
  2. It’s not the same as your iteration_count cap. iteration_count lives in the state and gates the supervisor’s logic. recursion_limit lives in the runtime and gates the graph’s execution. Both can be set independently; both can fire independently.
  3. GraphRecursionError is the exception you’ll catch in production. It is not recoverable mid-graph — by the time it raises, the graph has already given up. You can try/except it and surface a clean error to the user, but the state from that run is gone unless you have a checkpointer.
TWO-LAYER CAP PATTERN, IN ONE RULE

Put a tight MAX_ITERATIONS (3–5) in your supervisor state for application-level “the supervisor shouldn’t have to ask more than 3 workers” logic. Leave LangGraph’s recursion_limit at its default (25) as the last-line guard against pathological graph topologies. They protect against different failure modes; you want both.

§ 06 — THE REST API CONNECTION

Three secrets. Four endpoints. Bearer-token auth.

This is the new operational content of Session 25. The PDF code only runs inside a Databricks notebook because of the workspace SDK shortcuts. To run the same GenieAgent from a React app on Vercel, a Streamlit app on Azure, or a Next.js app on your laptop, you need three secrets and the right Bearer-token auth on three REST endpoints.

The three secrets

SECRETWHAT IT ISWHERE TO FIND IT
GENIE_SPACE_IDUUID-ish identifier for one Genie SpaceURL of the Genie Space: .../genie/rooms/<GENIE_SPACE_ID>
DATABRICKS_HOSTWorkspace URL prefixhttps://<workspace-id>.cloud.databricks.com (everything before /editor/...)
DATABRICKS_GENIE_PATPersonal Access TokenProfile → Settings → Developer → Access Tokens → Generate new token
  1. A workspace PAT inherits all of your access. Anyone with this token can hit any SQL Warehouse or Genie Space you can. Treat it like a database password — scope it tightly (expiration date, minimum required role) and store it in your platform’s secret manager.
  2. Delete the token when you stop using it. Especially on a paid Databricks workspace, an unused PAT is an attack-surface liability.

The endpoints (verified against docs.databricks.com/aws/en/genie/conversation-api)

Every request takes Authorization: Bearer <DATABRICKS_GENIE_PAT> and Host: <DATABRICKS_HOST>.

HTTPPATHPURPOSE
POST/api/2.0/genie/spaces/{space_id}/start-conversationStart a new conversation; body has the first message. Returns {conversation_id, message_id, ...}.
POST/api/2.0/genie/spaces/{space_id}/conversations/{conversation_id}/messagesSend a follow-up message in an existing conversation.
GET/api/2.0/genie/spaces/{space_id}/conversations/{conversation_id}/messages/{message_id}Poll a message for status (PENDING → COMPLETED / FAILED). Genie answers are not synchronous.
GET.../messages/{message_id}/query-result/{attachment_id}Fetch the SQL query result rows for a completed message.

Only POST requests count toward Genie’s per-minute throughput quota. GET polling is unmetered.

The Python SDK (databricks-sdk) and the GenieAgent wrapper from databricks-langchain hide this polling loop. The two-line equivalent looks like:

from databricks.sdk import WorkspaceClient
from databricks_langchain.genie import GenieAgent

client = WorkspaceClient(
    host=os.getenv("DATABRICKS_HOST"),
    token=os.getenv("DATABRICKS_GENIE_PAT"),
)
genie_agent = GenieAgent(
    genie_space_id=os.getenv("GENIE_SPACE_ID"),
    genie_agent_name="Genie",
    description="Queries NYC taxi-trip data.",
    client=client,
)
# Now use genie_agent as a LangGraph node, same as in the notebook.
JAVA / SPRING BRIDGE

Three secrets, one bearer-token auth scheme, four REST endpoints, a stateful conversation handle, and async polling for completion. If you’ve integrated with Salesforce, Stripe, or any modern enterprise API, you know this shape. The polling loop is the unusual bit — most CRUD APIs are synchronous, but anything that runs an LLM + SQL query under the hood has to be async because the latency is unpredictable. Build your client with a backoff (200ms → 400ms → 800ms jittered, capped at ~5s) and a timeout (30–60s); don’t tight-loop.

Dedicated SQL Warehouse — when to attach one

By default, a Genie Space uses the workspace’s Starter Warehouse — small, shared, slow on cold start. For a single demo this is fine. For a production-facing Genie endpoint, attach a dedicated SQL Warehouse:

  1. Compute → SQL Warehouses → Create a warehouse sized for the data (Small or Medium for most cases).
  2. Open the Genie Space → Settings → Default warehouse → pick the dedicated one.
  3. Cold-start drops from ~20s to ~2s; concurrent queries don’t queue.

Sasmita’s caveat applies double: a dedicated warehouse runs continuously while serving queries. Spin it down when you’re not using it or it will burn DBUs at the per-second rate of its size class.

§ 07 — Q&A: NEO4J vs DATABRICKS

The actually-useful reframe

The Q&A at the end asked a question every learner in this audience will hit:

“We used Neo4j in earlier sessions for multi-hop graph queries. Here we’re using SQL through Databricks. When do we use which?”

Sasmita’s answer, distilled:

WHENUSE
Source data is structured (rows × columns in a warehouse / lakehouse / RDBMS)Databricks + Genie. SQL on Spark scales to petabytes.
Source data is graph-shaped (entities + relationships, multi-hop reachability)Neo4j with a Cypher tool. Algorithms like shortest-path and community-detection don’t map cleanly to SQL.
Source data is unstructured text / documentsVector store + retrieval (Databricks ships a built-in databricks-vectorsearch tool; or use Neo4j + GraphRAG; or pgvector / Pinecone / Weaviate / Chroma).
You have all threeDon’t pick. Add all three as separate nodes under the same supervisor. The supervisor’s job is exactly to route based on question shape.

The last row is the actually-useful point. The whole reason LangGraph exists is that the worker types are not mutually exclusive. A real product almost always needs structured-data Q&A (Genie) and document retrieval (vector search) and maybe graph traversal (Cypher). One supervisor, three worker nodes, three descriptions tight enough that the supervisor picks correctly.

§ 08 — CLEANUP HYGIENE

Non-negotiable on a paid workspace

The lecturer interrupts mid-demo to say it twice: “please make sure once you know and then practice, you can delete immediately.” This is a sentence that gets ignored exactly until your AWS bill arrives.

Concrete checklist after each practice session on a paid Databricks workspace:

  • Stop the SQL Warehouse if you created a dedicated one for the Genie Space. (Compute → SQL Warehouses → ··· → Stop.) A stopped warehouse costs nothing; a running idle one bills per minute.
  • Delete the Personal Access Token from Settings → Developer → Access Tokens if it’s not in active use. PATs are the most-leaked Databricks credential type.
  • Delete the registered MLflow model version if you registered one for the demo. Each registered version holds storage.
  • Delete unused notebook outputs / large temp tables if you wrote anything to a Unity Catalog table during testing.
  • Stop any model serving endpoint that’s running. Idle endpoints can be the single largest line on a Mosaic AI bill.

The free-trial workspace gives you $400 of free credits, expiring 14 days from signup. A single Medium SQL Warehouse left running for a weekend will burn through most of that.

§ 09 — THE FULL GRAPH CODE, ANNOTATED

End-to-end agent.py from the PDF

import functools, os
from typing import Any, Generator, Literal, Optional

import mlflow
from databricks.sdk import WorkspaceClient
from databricks_langchain import ChatDatabricks, UCFunctionToolkit
from databricks_langchain.genie import GenieAgent
from langchain_core.runnables import RunnableLambda
from langgraph.graph import END, StateGraph
from langgraph.graph.state import CompiledStateGraph
from langgraph.prebuilt import create_react_agent
from mlflow.langchain.chat_agent_langgraph import ChatAgentState
from mlflow.pyfunc import ChatAgent
from mlflow.types.agent import (
    ChatAgentChunk, ChatAgentMessage, ChatAgentResponse, ChatContext,
)
from pydantic import BaseModel

# -- Genie node — wraps NL→SQL over a registered Genie Space --
GENIE_SPACE_ID = "01f00ecf37291f69a8ca023aa06af7b7"
genie_agent_description = (
    "This agent can answer queries based on stored datasets which consist of "
    "country-related tables. It can provide detailed explanations about the "
    "datasets and their capabilities."
)
genie_agent = GenieAgent(
    genie_space_id=GENIE_SPACE_ID,
    genie_agent_name="Genie",
    description=genie_agent_description,
    client=WorkspaceClient(
        host=os.getenv("DATABRICKS_HOST"),
        token=os.getenv("DATABRICKS_GENIE_PAT"),
    ),
)

# -- LLM endpoint (supervisor + ReAct nodes share it) --
LLM_ENDPOINT_NAME = "databricks-meta-llama-3-3-70b-instruct"
llm = ChatDatabricks(endpoint=LLM_ENDPOINT_NAME)
# PDF note: multi-agent Genie performs best with GPT-4o or GPT-o1.

# -- Coder node — a ReAct agent with Unity Catalog function tools --
tools = []
uc_tool_names = ["system.ai.*"]              # built-in UC fns (incl. python_exec)
uc_toolkit = UCFunctionToolkit(function_names=uc_tool_names)
tools.extend(uc_toolkit.tools)
code_agent_description = (
    "The Coder agent specializes in solving programming challenges, generating "
    "code snippets, debugging issues, and explaining complex coding concepts."
)
code_agent = create_react_agent(llm, tools=tools)

# -- Weather node — a pre-registered MLflow pyfunc model loaded from UC --
mlflow.set_registry_uri("databricks-uc")
agent_model_version_uri = "models:/tcs.test_sandip.ag_get_weather_python/1"
weather_agent = mlflow.pyfunc.load_model(agent_model_version_uri)
weather_agent_description = (
    "The weather agent specializes in returning the current weather of a given location."
)

# -- Supervisor node — LLM-with-structured-output, capped by iteration_count --
MAX_ITERATIONS = 3
worker_descriptions = {
    "Genie":   genie_agent_description,
    "Coder":   code_agent_description,
    "Weather": weather_agent_description,
}
formatted_descriptions = "\n".join(f"- {n}: {d}" for n, d in worker_descriptions.items())
system_prompt = (
    f"Decide between routing between the following workers "
    f"or ending the conversation if an answer is provided.\n{formatted_descriptions}"
)
options = ["FINISH"] + list(worker_descriptions.keys())

def supervisor_agent(state):
    count = state.get("iteration_count", 0) + 1
    if count > MAX_ITERATIONS:
        return {"next_node": "FINISH"}

    class nextNode(BaseModel):
        next_node: Literal[tuple(options)]              # pydantic-enforced enum

    preprocessor = RunnableLambda(
        lambda s: [{"role": "system", "content": system_prompt}] + s["messages"]
    )
    supervisor_chain = preprocessor | llm.with_structured_output(nextNode)
    next_node = supervisor_chain.invoke(state).next_node
    return {"iteration_count": count, "next_node": next_node}

# -- State, nodes, edges --
class AgentState(ChatAgentState):
    next_node: str
    iteration_count: int

def agent_node(state, agent, name):
    result = agent.invoke(state)
    return {"messages": [{"role": "assistant",
                          "content": result["messages"][-1].content,
                          "name": name}]}

def agent_node_existing_model(state, agent, name):
    # pyfunc models expose .predict(), not LangChain's .invoke()
    result = agent.predict(state)
    return {"messages": [{"role": "assistant",
                          "content": result["messages"][-1].content,
                          "name": name}]}

def final_answer(state):
    fa_prompt = ("Using only the content in the messages, respond to the user's "
                 "question using the answer given by the other agents.")
    pre = RunnableLambda(lambda s: [{"role": "system", "content": fa_prompt}] + s["messages"])
    return {"messages": [(pre | llm).invoke(state)]}

genie_node   = functools.partial(agent_node,                agent=genie_agent,   name="Genie")
code_node    = functools.partial(agent_node,                agent=code_agent,    name="Coder")
weather_node = functools.partial(agent_node_existing_model, agent=weather_agent, name="Weather")

workflow = StateGraph(AgentState)
workflow.add_node("Genie",        genie_node)
workflow.add_node("Coder",        code_node)
workflow.add_node("Weather",      weather_node)
workflow.add_node("supervisor",   supervisor_agent)
workflow.add_node("final_answer", final_answer)

workflow.set_entry_point("supervisor")
for worker in worker_descriptions.keys():
    workflow.add_edge(worker, "supervisor")           # workers report back

workflow.add_conditional_edges(
    "supervisor",
    lambda x: x["next_node"],                       # supervisor's choice
    {**{k: k for k in worker_descriptions.keys()},      # name → node
     "FINISH": "final_answer"},                       # FINISH → final_answer
)
workflow.add_edge("final_answer", END)
multi_agent = workflow.compile()

mlflow.langchain.autolog()                       # MLflow tracing for every span
AGENT = LangGraphChatAgent(multi_agent)
mlflow.models.set_model(AGENT)

§ 11 — QUIZ

Ten questions. Answers hidden in §12.

Q1. The supervisor node’s routing decision is implemented as:

  1. A regex match on the user message
  2. A LangChain MultiPromptChain with one prompt per worker
  3. llm.with_structured_output(NextNode) where NextNode is a Pydantic enum

§ 13 — GLOSSARY

Vocabulary in one place

ChatAgent
MLflow’s standard interface for LLM-agent serving. Lives in mlflow.pyfunc. Two methods: predict() → ChatAgentResponse, predict_stream() → generator of ChatAgentChunk.
ResponsesAgent
The MLflow-3.0+ successor to ChatAgent. Aligns with OpenAI’s newer Responses API. New code should prefer it.
CompiledStateGraph
The runtime form of a LangGraph workflow after workflow.compile(). The thing your ChatAgent wraps.
GenieAgent
LangChain/LangGraph-compatible wrapper for a Genie Space. Lives in databricks_langchain.genie. Takes genie_space_id, genie_agent_name, description, client=WorkspaceClient(...).
Genie Space
A Databricks UI artifact — a curated set of Unity Catalog tables that an LLM is allowed to query in natural language. The thing you create before writing any code.
recursion_limit
LangGraph’s per-invoke safety cap on the number of supersteps. Default 25. Configured via config={"recursion_limit": N}. Raises GraphRecursionError when exceeded.
MAX_ITERATIONS
(Notebook convention.) An application-level counter in the supervisor’s state that short-circuits to FINISH when worker-routing exceeds a small number. Not the same as recursion_limit.
Supervisor
An LLM call that returns structured output deciding which worker to call next. Quality bounded by worker descriptions in the system prompt.
UCFunctionToolkit
A LangChain toolkit that exposes Unity Catalog functions (Python or SQL) as agent tools. function_names=["system.ai.*"] pulls in the built-in functions, including python_exec.
mlflow.langchain.autolog()
One-liner that turns on MLflow Tracing for LangChain/LangGraph by hooking into LangChain’s callback system. Every node/llm/tool call gets its own trace span.
PAT (Personal Access Token)
Databricks workspace credential. Created at Settings → Developer → Access Tokens. Inherits the full access of the creating user. Treat as a database password.
SQL Warehouse
The compute that runs the SQL Genie generates. Default is the “Starter Warehouse” (small, shared). For production Genie endpoints, attach a dedicated warehouse and stop it when idle.
DBU
Databricks Unit of cost. The billing unit. Spinning compute = burning DBUs. Stopped = $0.
mlflow.set_registry_uri("databricks-uc")
Configures MLflow to use Unity Catalog as the model registry. Required for loading models via models:/catalog.schema.model/version.
