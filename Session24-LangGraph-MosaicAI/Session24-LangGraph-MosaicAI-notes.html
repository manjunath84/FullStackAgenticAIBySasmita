Wiring LangGraph
into Databricks

Genie agents, Unity Catalog tools, and the MLflow ChatAgent wrapper that turns your LangGraph into a deployable Databricks artefact.

67 MIN 1 SPEAKER EN_US 2026-05-20
Genie and the Unity Catalog tools are adapters into Databricks state. The orchestration — what calls what, in what order — stays in your LangGraph. The job of this session is to learn the three lines of glue that put a GenieAgent and a create_react_agent into a graph the same way you'd put any other node.
00 · WHERE WE ARE

Where we are

Session 23 introduced Databricks as a platform — Unity Catalog (the catalog.schema.table hierarchy), the medallion architecture, the Genie text-to-SQL agent, MLflow, the in-notebook Playground. We saw what a Genie Space is, how to register a table to it, and how to ask questions in plain English.

This session goes one layer down: how do you reach Genie from your own LangGraph code? The lecturer walks through the official Mosaic AI Agent Framework example end-to-end — Genie agent, Unity Catalog function tools, supervisor agent, and the MLflow ChatAgent wrapper that adapts everything to Databricks' deployment surface. The whole point is one sentence: your LangGraph flow does not have to be rewritten to run on Databricks; you wrap it.

The lecturer promised the full New York Taxi end-to-end build for "tomorrow" — that's Session 25, where two Genie spaces (taxi + customer-sales) will be routed by a single supervisor.

01 · GENIE SPACE, RECAPPED

The Genie space, briefly recapped

A Genie space is a curated bundle of one or more Unity Catalog tables, plus a description, plus a small library of (natural-language question → SQL query) example pairs, that turns into a text-to-SQL agent. You ask in English; Genie writes the SQL against the bundled tables and returns the result. It is the production-grade answer to "can we have a Text2SQL?" — which LangChain already shipped, but with a fatal weakness: it has no opinion about the data dictionary.

What makes Genie work where LangChain's SQLDatabaseChain doesn't is discipline at the catalog layer, not at the prompt layer:

  1. Every table and every column must have a description in Unity Catalog metadata. The data engineering team should add the data dictionary at load time, not the agent author after the fact. If the descriptions are missing, you can patch them in the Genie space Instructions panel — but that's a workaround, not the right place.
  2. Add example SQL queries for the questions your users will actually ask. The lecturer's number: up to 100 example pairs are loaded into the Genie space at session start. When a user asks a question that matches one of the examples, Genie executes the bundled SQL directly, with confidence, instead of regenerating.
  3. One Genie space per use case. Do not pile 30 tables into one space — the agent gets confused about joins. Create separate spaces with 1–3 tables each.

Why this matters. A LangChain text-to-SQL chain prompts the LLM with the schema every call, hopes the schema you wrote is the schema that exists, and has no source of truth when the data team adds a column. Genie inherits its schema from Unity Catalog at runtime, so when the data team adds a column, your code keeps working without redeploy. The boundary that breaks LangChain's text-to-SQL — the data dictionary — has been moved from your prompt into the data team's job.

FAILURE TELL

When Genie returns the wrong column, look in Unity Catalog metadata first — not at the prompt. The description on the column is almost always blank or wrong.

How to grab a Genie space ID

Open the Genie space. Look at the URL. Copy the path segment before the ? — that long alphanumeric string is your space ID. You will paste it into your code in exactly one place.

03 · UC FUNCTION TOOLS

Unity Catalog function tools — built-in, not built-by-you

Unity Catalog is not just a catalog of tables; it's also a catalog of functions. Databricks ships a large set of built-in functions under the schema system.ai. You don't write them; they exist on every workspace.

FunctionWhat it does
system.ai.python_execSandbox Python execution — lets any LLM run code without you writing a Python tool.
system.ai.ai_queryRoute a prompt to a foundation-model endpoint — Databricks' "ask any LLM" helper.
system.ai.ai_classifyLLM-backed classifier — label set + input → label.
system.ai.ai_extractLLM-backed structured extraction (entities, fields).
system.ai.ai_summarizeLLM-backed summarization.
system.ai.ai_translateLLM-backed translation.
system.ai.ai_genOpen-ended LLM generation.
system.ai.vector_searchQuery a Databricks Vector Search index.

You can also register your own functions into Unity Catalog — they live alongside system.ai and get the same governance (access control, lineage, version tracking) as the built-ins.

To make all of these visible to an LLM agent, wrap them in a UCFunctionToolkit:

from databricks_langchain import UCFunctionToolkit

uc_tool_names = ["system.ai.*"]                # everything under system.ai
toolkit = UCFunctionToolkit(function_names=uc_tool_names)
tools = toolkit.tools                          # list of LangChain Tool objects

"system.ai.*" is a wildcard meaning "every function in system.ai". You can also list specific functions: ["system.ai.python_exec", "main.utilities.my_function"].

JAVA / SPRING BRIDGE

UCFunctionToolkit(function_names=["system.ai.*"]) is @ComponentScan(basePackages = "system.ai"). You're not declaring which beans to use; you're declaring a package to scan, and the framework discovers everything that matches and wires it for you.

FAILURE TELL

When an agent says "I can do X" and then fails to call the matching tool, check that the function is actually under the wildcard you passed. system.ai.* does not include functions you wrote into main.utilities.*.

04 · THE TWO AGENTS

The two agents Databricks ships in this example

The lecturer's example builds two ready-made agents from databricks-langchain.

GenieAgent — wraps a Genie space, has no LLM

from databricks_langchain.genie import GenieAgent

genie_agent = GenieAgent(
    genie_space_id="01ef...",                  # your space ID
    genie_agent_name="Genie",                  # for tracing / observability
    description="Answers questions about NY taxi trip data.",
)

The crucial point — and one the lecturer flagged because it confuses everyone — GenieAgent does not contain an LLM call. There is no model= argument. It's a thin handle that points at a Genie space. The LLM that writes the SQL is inside Genie, on the Databricks side. You're not building an agent; you're registering a reference to a Databricks-side agent so LangGraph can call it like any other node.

If you look at the constructor signature, only genie_space_id is mandatory. The name and description exist so that when MLflow traces this run later, you can tell which Genie space was hit. Always set them — without names, a 10-agent trace looks like a wall of agent_0, agent_1, …

The Code Agent — a ReAct agent over the Unity Catalog tools

from databricks_langchain import ChatDatabricks
from langgraph.prebuilt import create_react_agent

llm = ChatDatabricks(endpoint="databricks-meta-llama-3-1-70b-instruct")

code_agent_description = (
    "Runs Python or SQL via the Unity Catalog system.ai tools. "
    "Use for arithmetic, code execution, classification, summarization, "
    "translation, extraction, generation, and vector search."
)

code_agent = create_react_agent(
    model=llm,
    tools=tools,                                # from UCFunctionToolkit
    name="Coder",
)

This one does contain an LLM. create_react_agent is the LangGraph prebuilt that implements the ReAct pattern — a two-node loop where the LLM either answers directly or emits a tool call, the tool node executes the call, and the LLM sees the result and decides whether to call another tool or finish.

ChatDatabricks is the LangChain-style chat-model class for any model endpoint hosted in Databricks Foundation Model APIs — open-weight models (Llama, gpt-oss-120b, Mistral, DBRX), proprietary models (Claude, GPT family via partner endpoints), or custom fine-tunes you deployed. Same .invoke() interface as ChatOpenAI or ChatAnthropic.

Why the asymmetry

GenieAgent is a destination; code_agent is an engine. Genie has its own LLM and its own logic on the Databricks side — you only need to point at it. The Code agent is just an LLM + tool list assembled on your side and given a name. The fact that both end up as nodes in the same LangGraph is what makes the pattern composable.

JAVA / SPRING BRIDGE

GenieAgent is a Spring @Component that holds an ExternalServiceConfig — connection string, no business logic. create_react_agent is a Spring @Service with a strategy bean injected and a @PostConstruct that wires the strategy to a list of helper components. Both expose the same interface, so the caller doesn't know one is hollow and the other is fat.

05 · SUPERVISOR PATTERN

The supervisor pattern — routing among workers with a hard iteration cap

So far we have three nodes the supervisor will route to: Genie, Coder, and (in the lecturer's example) a third Weather node that wraps a small custom function. The supervisor is itself an LLM call whose job is to pick which worker should handle the next user message.

Two things make this not a simple conditional edge:

  1. Multiple paths. Previous LangGraph sessions (Sessions 21–22) showed binary conditional edges — if-this-else-that. Here we have N possible routes. The graph must add an edge from supervisor to each worker, which means a for loop over the worker names.
  2. Loop risk. A supervisor that can route back to itself can ping-pong forever. The lecturer's pattern adds an explicit iteration counter to the graph state and a hard cap (her choice: 3 iterations); past the cap, the supervisor routes to FINISH regardless of what the LLM picked.

The state object

from typing import Optional, Annotated, Sequence, TypedDict
from langgraph.graph.message import add_messages
from langchain_core.messages import BaseMessage

class AgentState(TypedDict):
    messages: Annotated[Sequence[BaseMessage], add_messages]
    next_node: Optional[str]                       # who the supervisor picked
    iteration_count: int                           # how many supervisor hops so far

messages is the running conversation, accumulated by add_messages (the LangGraph reducer that appends). next_node is the name of the worker the supervisor most recently picked. iteration_count is how the loop is bounded.

The supervisor itself

The supervisor node is an LLM call with a structured output schema constrained to the worker names plus FINISH. Structured output is the LangChain mechanism (.with_structured_output(Schema)) that forces the LLM to return a parseable object instead of free text. Without it, the supervisor returns "I think we should go to the Coder agent" and you have to regex-parse it.

from pydantic import BaseModel, Field
from typing import Literal

worker_names = ["Genie", "Coder", "Weather"]
options = worker_names + ["FINISH"]

class Route(BaseModel):
    next_node: Literal["Genie", "Coder", "Weather", "FINISH"] = Field(
        description="Which worker should handle the next step, or FINISH if done."
    )

SUPERVISOR_PROMPT = """You are a supervisor routing user requests to worker agents.
Workers: {worker_descriptions}
Pick exactly one of {options} as next_node. Choose FINISH when no further work is needed.
"""

def supervisor_node(state: AgentState) -> AgentState:
    if state["iteration_count"] >= 3:
        return {"next_node": "FINISH", "iteration_count": state["iteration_count"]}
    chain = preprocessor | llm.with_structured_output(Route)
    result = chain.invoke({"messages": state["messages"]})
    return {
        "next_node": result.next_node,
        "iteration_count": state["iteration_count"] + 1,
    }

Wiring the edges

from langgraph.graph import StateGraph, START, END

workflow = StateGraph(AgentState)
workflow.add_node("Genie",   genie_node)
workflow.add_node("Coder",   code_node)
workflow.add_node("Weather", weather_node)
workflow.add_node("supervisor",   supervisor_node)
workflow.add_node("final_answer", final_answer_node)

workflow.add_edge(START, "supervisor")

# every worker reports back to the supervisor
for worker in worker_names:
    workflow.add_edge(worker, "supervisor")

# the supervisor's conditional routing
def route_from_supervisor(state: AgentState) -> str:
    return state["next_node"]

workflow.add_conditional_edges(
    "supervisor",
    route_from_supervisor,
    {name: name for name in worker_names} | {"FINISH": "final_answer"},
)

workflow.add_edge("final_answer", END)
multi_agent = workflow.compile()

The final-answer node

After the supervisor routes to FINISH, the final_answer node aggregates the conversation and asks the LLM to produce the user-facing reply. It's a small chain — preprocessor (system prompt) → llm → return the message — that exists so the user gets one coherent answer rather than the last worker's raw output.

JAVA / SPRING BRIDGE

The supervisor is a router @Service that consults a strategy enum to pick which @Component to delegate to. The iteration cap is the same pattern as a @Retryable handler — bounded retries before falling back to a graceful exit. The conditional edge is your switch statement; the for loop that adds edges is the line in @PostConstruct that registers every @Component implementing your Worker interface.

FAILURE TELL

When the agent runs forever or returns the same answer three times, look at iteration_count. The supervisor is being asked to re-route on a state that hasn't changed; either the worker isn't updating messages, or the supervisor's prompt isn't strong enough to recognize "we're done."

06 · CHATAGENT WRAPPER

The MLflow ChatAgent wrapper — why it exists and what it adapts

The compiled multi_agent graph above is a perfectly good LangGraph runnable. You can .invoke({"messages": [...]}) it locally and get an answer. But Databricks' agent deployment surface — Mosaic AI Agent Framework, MLflow logging, Agent Bricks evaluation — expects a specific Python interface: mlflow.pyfunc.ChatAgent.

ChatAgent is an abstract class with a small contract — implement predict() (and optionally predict_stream()), and Databricks knows how to serve, log, evaluate, and govern your agent. Mosaic AI Agent Framework documentation lists it as the recommended interface for any multi-turn conversational agent built on Databricks, regardless of authoring framework (LangGraph, LangChain, LlamaIndex, OpenAI Agents SDK).

The wrapper is mechanical. You will copy-paste it almost verbatim from the Databricks tutorial:

from typing import Any, Generator, Optional
from mlflow.pyfunc import ChatAgent
from mlflow.types.agent import (
    ChatAgentChunk, ChatAgentMessage, ChatAgentResponse, ChatContext,
)

class LangGraphChatAgent(ChatAgent):
    def __init__(self, agent):
        self.agent = agent                          # the compiled LangGraph

    def predict(self, messages, context=None, custom_inputs=None) -> ChatAgentResponse:
        request = {"messages": self._convert(messages)}
        result = self.agent.invoke(request)
        final = result["messages"][-1]
        return ChatAgentResponse(messages=[
            ChatAgentMessage(role="assistant", content=final.content)
        ])

    def predict_stream(self, messages, context=None, custom_inputs=None) -> Generator[ChatAgentChunk, None, None]:
        request = {"messages": self._convert(messages)}
        for chunk in self.agent.stream(request, stream_mode="messages"):
            yield ChatAgentChunk(delta=ChatAgentMessage(role="assistant", content=chunk[0].content))

    @staticmethod
    def _convert(msgs):
        return [{"role": m.role, "content": m.content} for m in msgs]

AGENT = LangGraphChatAgent(multi_agent)

After this, AGENT.predict(messages=[...]) is the only thing Databricks calls. Your entire LangGraph multi-agent flow lives behind this one method.

JAVA / SPRING BRIDGE

The ChatAgent wrapper is a @RestController adapter on a business @Service. The service does the work (your LangGraph). The controller exposes that work through the framework's expected interface (here, MLflow / Mosaic AI). Same logic, two skins. Nothing about multi_agent changes; you've just made it speak the platform's protocol.

Why you can't skip it

Without the wrapper, the LangGraph runs but Databricks-side features don't work:

  • MLflow autolog can't trace it correctly (no ChatAgent schema to attach to)
  • Agent Bricks evaluation can't score it (the scorer expects ChatAgentResponse)
  • Mosaic AI Agent Framework deployment can't serve it (the serving endpoint expects the predict signature)
  • Multi-turn conversation tracking breaks (the platform doesn't know how to thread messages)

You get all four of those by adding twenty lines of wrapper code, so there is no reason not to.

FAILURE TELL

When MLflow traces look empty or mlflow.evaluate errors with "no predictions logged," check that you logged the wrapped AGENT, not the raw multi_agent. The platform doesn't follow LangGraph internals; it only sees what ChatAgent.predict() returns.

Transcript correction.

The transcript places ChatAgent "by Databricks" — close enough verbally but technically wrong. ChatAgent lives in MLflow (mlflow.pyfunc.ChatAgent, with message types in mlflow.types.agent). Mosaic AI Agent Framework recommends it; Databricks did not author it. The MLflow OSS project owns the class.

07 · FROM OUTSIDE DATABRICKS

Connecting from outside the Databricks notebook — WorkspaceClient

When you run this code inside a Databricks notebook, the workspace identity is implicit — no auth setup, the kernel runs as you. When you run it from your laptop (VS Code, plain Python), you need to tell the SDK who you are and where to connect.

from databricks.sdk import WorkspaceClient
client = WorkspaceClient()                         # picks up env vars

WorkspaceClient() with no arguments reads from environment variables. The minimum:

DATABRICKS_HOST=https://<workspace>.cloud.databricks.com
DATABRICKS_TOKEN=dapi...

You get the token from Settings → Developer → Access tokens → Generate new token in your workspace. Treat it like a password — never commit it to git; load it from .env via python-dotenv, or from your platform's secret store.

For Genie specifically, two more variables are commonly used to point at the Genie REST endpoint:

DATABRICKS_GENIE_API_HOST=https://<workspace>.cloud.databricks.com
DATABRICKS_GENIE_SPACE_ID=01ef...

In a Databricks notebook you don't need any of this — the kernel has implicit auth. The lecturer's example is shown both ways: the notebook version skips the client, the VS Code version creates one. Treat the client as a transport detail — the agent code itself doesn't care.

08 · AGENT BRICKS VS HAND-CODED

Agent Bricks "Export agent" vs hand-coded LangGraph

Inside the Databricks Playground you can build an agent visually: pick a model, pick tools (Unity Catalog functions, MCP servers, vector search, your custom functions), click Get Code → Export agent notebook, and Databricks generates a runnable notebook implementing your agent end-to-end, including evaluation and deployment.

That generated notebook is what Databricks calls Agent Bricks code. It's clean, opinionated, production-ready, and — the lecturer's point — it does not use LangGraph. Databricks' Agent Bricks generator emits its own orchestration code with MLflow ChatAgent at the top. It's great for a single-flow agent; it's limiting if you want LangGraph features the generator doesn't emit (subgraphs, human-in-the-loop, checkpointing, custom reducers).

Use Agent Bricks "Export agent" when…Hand-code LangGraph when…
You want a quick scaffold to start fromYou need LangGraph features (subgraphs, custom state, checkpointing, human-in-the-loop)
Your agent is one ReAct loop + toolsYou have a real multi-agent topology with supervisor routing
You want maximum Databricks-native integration with zero codeYou want the same code to run outside Databricks (portability)
You're learning the platformYou already have a LangGraph codebase and need to move it onto Databricks

The bridge is the ChatAgent wrapper from §6. Whichever side you author on, both sides land at the same interface, and Databricks treats them identically.

09 · CANONICAL ORDER

Putting it all together — the canonical assembly order

Eight steps, in the order the lecturer recommends:

  1. Create the Genie space in the Databricks UI. Register the table, add the description, add 1–100 example (question → SQL) pairs. Copy the space ID.
  2. Create the GenieAgent with that space ID. No LLM, no model — just the ID and a description.
  3. Create the ChatDatabricks LLM endpoint with the foundation model you want (gpt-oss-120b, Llama 3.1 70B, DBRX).
  4. Build the UCFunctionToolkit with ["system.ai.*"] or the specific functions you need. Extract toolkit.tools.
  5. Create the Code agent via create_react_agent(model=llm, tools=tools). Give it a name and a description.
  6. Add any custom worker (e.g., a weather function) as a third agent. Wrap it in a small node function returning the state-update shape LangGraph expects.
  7. Define the supervisor and the state, wire the graph with add_node + add_edge + add_conditional_edges. Compile.
  8. Wrap the compiled graph in LangGraphChatAgent(ChatAgent). Log it with MLflow (mlflow.pyfunc.log_model) when you're ready to deploy.

The first time you write this, steps 7 and 8 take most of the time. Every subsequent multi-agent build, steps 1–6 are the only ones that change.

Glossary

Agent Bricks
Databricks' governed agent-platform layer; provides Unity Catalog access control, MLflow CLEARS-style evaluation, supervisor-agent orchestration helpers, and one-step deployment. Not a LangGraph replacement; sits above the authoring framework.
ChatAgent
Abstract class in mlflow.pyfunc that defines the interface (predict, predict_stream) Databricks expects from any conversational agent. The recommended deployment wrapper.
ChatDatabricks
Chat-model class in databricks-langchain that wraps a Databricks foundation-model endpoint behind LangChain's chat-model interface.
create_react_agent
LangGraph prebuilt (langgraph.prebuilt.create_react_agent) that constructs a ReAct-pattern agent: LLM node + tool node + loop until the LLM returns no tool call.
GenieAgent
Class in databricks-langchain that wraps a Genie Space as a LangGraph-callable agent. Holds the space ID; contains no LLM of its own.
Genie space
A configured bundle of Unity Catalog tables + descriptions + example (NL → SQL) pairs that becomes a text-to-SQL agent on Databricks.
gpt-oss-120b
OpenAI's open-weight 120B-parameter model (Apache 2.0, August 2025). Available as a foundation-model endpoint in Databricks.
Mosaic AI Agent Framework
Databricks' framework for building, evaluating, and deploying production AI agents. Recommends mlflow.pyfunc.ChatAgent as the agent interface.
MLflow
Open-source ML lifecycle platform (LF AI Foundation). Bundled into Databricks. Provides experiment tracking, model registry, deployment, evaluation, and the ChatAgent agent interface.
ReAct pattern
Agent design where the LLM alternates between reasoning steps and tool calls until it produces a final answer. Canonical loop: LLM → tool node → LLM → tool node → … → final answer.
Supervisor agent
A routing agent that, on each step, picks which worker agent should run next. Implemented here as a LangGraph node with a structured-output LLM picking from Literal[worker_name, …, "FINISH"].
Structured output
.with_structured_output(Schema) on a LangChain chat model — forces the LLM to return an object conforming to the Pydantic schema instead of free text.
Unity Catalog
Databricks' unified governance layer for data and AI assets. Three-level namespacing: catalog.schema.object. Stores tables, volumes, models, and functions (including system.ai.*).
UCFunctionToolkit
Class in databricks-langchain that turns a list of Unity Catalog function names (or a * wildcard) into a list of LangChain Tool objects an LLM agent can call.
WorkspaceClient
Entry-point class in databricks-sdk for talking to a Databricks workspace from outside (e.g., from VS Code). Reads DATABRICKS_HOST and DATABRICKS_TOKEN from the environment.
