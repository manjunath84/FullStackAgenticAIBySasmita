Unity Catalog, Genie, and the part of the stack a LangGraph agent actually needs.

The Java/Spring engineer who used to hand-write SQL on top of someone else's warehouse now writes a prompt against a governed catalog — and the same platform stores the data, runs the agent, serves the model, and tracks the experiment.

01 · THE 30-SECOND ANSWER

Why a warehouse vendor matters to an agent builder

Every demo so far has been built around text, audio, or video. Real enterprises run on structured data — claim forms, member tables, transaction ledgers, hospital codes — and that's where the dollars live. Banking is almost entirely structured. Healthcare is half-structured (claims) and half-unstructured (notes, scans). Even the unstructured stream usually ends up extracted into a table.

A LangGraph agent that can only answer questions about PDFs is therefore a toy. A LangGraph agent that can ask "what is the West-Asia sales delta from March to April 2026?" against a 525-column claims table and get a correct answer is a product. The hard part is the second one — and that is the gap Databricks closes.

The pitch in one line, copied from the Databricks marketing page the lecturer pulled up:

"A unified, open analytics platform for building, deploying, sharing, and maintaining enterprise-grade data analytics and AI solutions at scale."

The reason an agent course teaches it: agents need a place to put structured data, govern it, and ask questions of it. Databricks is the dominant answer in Azure/AWS shops. (BigQuery is the GCP answer; Snowflake is the cloud-agnostic competitor.)

02 · COMPUTE MODELS

Parallel vs distributed processing (and what Spark is for)

The lecturer makes a sharp split before introducing Spark:

  • Parallel processing. One big machine with many GPU cores doing the same operation on different slices of one data structure. Training a Transformer fits here — the gradient updates touch every parameter every step, so the workload doesn't decompose cleanly across separate machines.
  • Distributed processing. Many machines, each holding part of the data, executing part of the logic, with a coordinator aggregating results. This is what Spark does. SQL joins, group-bys, streaming aggregates, classical ML — these decompose cleanly, so distributing them across a cluster wins.

A distributed engine is the software that orchestrates this — the master holds a logical plan, the workers hold data partitions, the coordinator stitches results. Spark is the canonical one.

Correction (transcript §parallel-vs-distributed). The transcript says "deep learning cannot be distributed". That is too strong. Distributed deep-learning training is standard practice: data parallelism (each worker holds a copy of the model and a different mini-batch), model parallelism (the model itself is split across devices), pipeline parallelism, and frameworks like PyTorch FSDP and DeepSpeed ZeRO exist specifically for this.

The narrower claim is correct: Spark's MapReduce-style execution model is the wrong fit for dense gradient-based training, so Spark MLlib stops at classical ML (logistic regression, trees, k-means, ALS). Databricks does distributed deep learning, but through different runtimes (TorchDistributor, Mosaic AI Training, Horovod), not through Spark itself.

Correction (transcript §big-data-history). The transcript groups "Hadoop and all" as "nothing but Spark". They are different projects. Hadoop is HDFS (a distributed filesystem) plus MapReduce (a job framework), released 2006. Spark is a separate execution engine from UC Berkeley's AMPLab (2009) that often runs on top of HDFS or YARN but is not Hadoop. The "Hadoop, big data" hype of 2015–16 the lecturer remembers was the moment Spark started displacing MapReduce as the engine inside Hadoop clusters.

FAILURE TELL

When someone says "we'll just train it on Spark," ask which runtime — TorchDistributor or MLlib. If the answer is MLlib, the model is not a neural network.

The reason this matters for the rest of the lecture: Spark is Databricks' execution engine, and Databricks was founded by Spark's creators (Matei Zaharia and the UC Berkeley AMPLab team, 2013). When you pay Databricks, you're paying for managed Spark plus the layers built on top — catalog, governance, dashboards, agents, model serving.

JAVA BRIDGE · DISTRIBUTED VS PARALLEL

Distributed Spark is closer to a @KafkaListener consumer group on the same topic — many JVMs, each consuming a partition, results aggregated downstream — than to a single fat JVM with a parallelStream() running on 64 cores. Both have their place. Transformers are the fat-JVM-with-GPU story; a 171-million-row claims aggregation is the consumer-group story.

04 · UNITY CATALOG

The 3-layer model: catalog → schema → table

Every dataset in Databricks lives at a path with exactly three segments:

  • Catalog — top-level namespace, usually one per major business unit or project family (fraud_detection, nextgen). System is the default catalog every workspace gets.
  • Schema — second-level namespace inside a catalog, usually one per project (drg_shift, claims_q2).
  • Table — structured (rows and columns). Backed by Delta Lake by default.
  • Volume — unstructured (PDFs, images, raw files). What you store before extracting text.
  • View — saved query exposing a subset of a table; used to expose only the columns one team is allowed to see.

Access control hangs on this hierarchy. The data engineer creates fraud_detection.drg_shift.claims; the admin grants team_1 read on member view, team_2 write on hospital view. One place enforces it for every consumer — SQL editor, dashboard, Genie, LangGraph agent, Databricks App.

JAVA BRIDGE · CATALOG HIERARCHY

Think of catalog → schema → table as com.acme.fraud → drg_shift → ClaimsTable. Then layer Spring Security's @PreAuthorize("hasRole('TEAM_1')") per bean. Unity Catalog is exactly that, but enforced at the storage layer rather than in application code — so a rogue SQL query, a Power BI dashboard, or a Genie prompt all hit the same gate.

Why this layout is mandatory: Genie, MLflow models, dashboards, and Databricks Apps all address data by its three-part name. Skip the catalog and the agent has nothing to point at.

05 · MEDALLION ARCHITECTURE

Bronze, silver, gold

Three layers, named like Olympic medals, used by the data-engineering team to stage transformations:

  • Bronze — raw ingest, no cleaning. The claim form as it arrived.
  • Silver — cleaned and conformed. Nulls filled, types coerced, duplicate keys resolved.
  • Gold — query-ready subset for one consumer. "Some other team needs hospital addresses, so they create another table from the raw data, clean data, and they provide to them."

Each team gets a gold table tailored to it, with its own access grants. An AI engineer consuming the warehouse should expect to ask for a gold layer, not the bronze dump. "Data engineering will get the gold-layer data, which is clean and everything."

06 · GENIE

Text-to-SQL as a tool

This is the section the rest of the lecture builds toward. Genie is Databricks' first-party text-to-SQL agent. Its outputs: an executed SQL query, a result table, an auto-generated chart, and an explanation. Its inputs: a Genie Space (a curated bundle of tables + instructions) and a natural-language prompt.

6.1 — Why text-to-SQL on enterprise tables is hard

LangChain ships a SQLDatabaseChain that can do toy text-to-SQL. It falls apart on real enterprise schemas, and the reason is mundane:

"In my organization, the claim form has 525 columns. Every column is important. The agent will be confused when your user is asking. It will write the SQL code, but it will take the wrong columns."

The model can't fit a 525-column schema in its context window with enough description to disambiguate member_id_v2 from subscriber_id_legacy. When two columns sound similar, it picks the wrong one and silently returns the wrong answer. Silent-wrong is the worst failure mode for analytics.

6.2 — The fix: a curated Genie Space

A Genie Space is the unit of configuration. It holds:

SlotWhat it doesWhy it matters
Selected tablesWhich catalog.schema.table entries are in scopeLimits the column count the model has to reason over
Display name + description per columnHuman-friendly rename + one-line meaningDisambiguates similar columns; mandatory for accuracy
Hidden columnsColumns Genie is told never to seeCuts noise on 400-column tables where 10 are actually queried
General instructionsSystem-prompt-style business rules (patient_key = first + last + member_id)Encodes domain logic the SQL can't infer from column names
JoinsPre-declared join conditions between tablesGenie reuses the correct ON clause every time, never guesses
SQL expressions / saved queriesFrequently-asked questions with hand-written SQLGenie calls these as tools instead of re-planning

The Genie Space carries an ID. That ID is the integration point — from a Streamlit app, LangGraph node, Slack bot, or curl call you hit:

POST /api/2.0/genie/spaces/{space_id}/start-conversation

and poll the response endpoints until the message status concludes (the docs recommend 5–10 second polling, 10-minute max, exponential backoff after 2 minutes of no response).

This is what Session 24 will wire up.

JAVA BRIDGE · GENIE SPACE

Think of a Genie Space as a @RestController with an OpenAPI spec — but the OpenAPI spec is the column descriptions, the system prompt is the general instructions, and the pre-baked SQL queries are like @Cacheable request handlers for the questions you already know users will ask. The Space ID is the URL prefix.

6.3 — How Genie behaves at runtime

When you ask Genie "what is the distribution of trip distance — min, max, average, median?" the UI shows a two-row plan:

  1. Planner agent — decomposes the question into subtasks.
  2. SQL generator — writes SELECT MIN(trip_distance), MAX(trip_distance), AVG(trip_distance), PERCENTILE_CONT(0.5) WITHIN GROUP (ORDER BY trip_distance) FROM trips; or equivalent, runs it, renders a chart.

You can download the result, download the SQL, share to a teammate, click "not useful — poor visualization" and re-ask. The whole panel is exposable via the Conversation API — what you see in the UI is what an external app gets back.

6.4 — Failure tells

  • Wrong column picked, silently — the column description is missing or two columns have near-identical names. Fix: write the description; if you have authority, hide the duplicate.
  • Wrong join — Genie inferred a join that doesn't match your domain (e.g., joining claims.member_id to provider.member_id when those are different namespaces). Fix: declare the join explicitly in the Genie Space.
  • Hallucinated metric — Genie invented a column. Fix: this only happens when descriptions are absent. The lecturer is firm: "this is mandatory before even you start coding."
  • Genie refuses or stalls on a complex chart-comprehension question — the lecturer's own test (asking Genie to interpret a correlation already drawn on a dashboard) failed. Genie is strong on text-to-SQL, weaker on chart-introspection. Use it for what it's good at.
THE LECTURER'S STRONG CLAIM · KEEP AS HER CLAIM

"99.9% accurate if you have properly loaded your data and have a data dictionary."

This is the lecturer's production experience, not a benchmark — treat as illustrative. The right way to phrase it in an interview: "with a curated Genie Space, my team observed near-zero column-selection errors on a 525-column claims table."

07 · AGENT BRICKS

AgentBricks vs LangGraph

The transcript frames AgentBricks as "like LangGraph but less advanced — lot of components are missing, you can't go back to the parent from a child node like in LangGraph". This is the part of the lecture that is most off.

Correction (transcript §agentbricks). Agent Bricks is not a LangGraph alternative. It is Databricks' enterprise platform layer for agents. It supports LangGraph, LangChain, LlamaIndex, and the OpenAI Agents SDK as the agent-authoring framework.

What Agent Bricks adds on top: Unity Catalog governance applied to model and tool access, the CLEARS evaluation framework (Correctness, Latency, Execution, Adherence, Relevance, Safety) tracked in MLflow, a Supervisor Agent pattern for multi-agent orchestration, and one-step serverless deployment to Databricks Apps. The lecturer's intuition — "we will use LangGraph, not AgentBricks" — is right for the wrong reason. You're already using both as soon as you deploy a LangGraph agent into a Databricks workspace.

When to reach for each:

QuestionAnswer
I need conditional edges, cycles, custom stateLangGraph (the authoring layer)
I need to govern which user / role / app can call which modelAgent Bricks via Unity Catalog
I need standardized agent quality eval (CLEARS) plumbed into MLflowAgent Bricks
I need to ship a multi-agent workflow into a Databricks App in one clickAgent Bricks
I'm prototyping in a notebookLangGraph in the notebook, deploy later via Agent Bricks
JAVA BRIDGE · STARTERS VS RAW SPRING

Agent Bricks is to LangGraph as Spring Boot starters are to raw Spring Framework. Starters give you opinionated wiring, sane defaults, and one-step deploy; raw Spring gives you control over every bean. You use both — starters for the deploy, raw Spring for the bits the starter doesn't cover.

08 · THE REST

The rest of the surface area

The lecturer skimmed a number of features that you'll encounter without re-introduction. The minimum mental model for each:

Lakebase

Fully-managed serverless Postgres, powered by Neon, announced June 2025 Public Preview and February 2026 GA. Different from a Delta table: Lakebase is the OLTP store an application writes to (think: user profiles, session state, the table behind a Spring JdbcTemplate); a Delta table is the OLAP store you analyze. Lakebase's distinctive feature is copy-on-write branching — an agent can spin up a Lakebase clone, mutate it, validate the result, and merge or discard, the way git branch works. Useful for "agent tests a destructive query against a sandbox before running for real."

AI/BI Dashboards

Power-BI-style drag-drop dashboards with Genie embedded for ad-hoc questions on the chart. "You cannot compete with Databricks. They are the pioneer." The lecturer's caveat: Genie's chart-introspection (ask Genie about a chart already drawn) is weaker than Genie's text-to-SQL.

MLflow

Experiment tracking, model registry, model serving, and — now — the eval framework Agent Bricks plugs into for the CLEARS scores. "From next batch onwards I am removing LangFuse and adding MLflow." For this batch, LangFuse is still the observability layer for LangGraph agents; MLflow is what you use for traditional ML lifecycle and increasingly for agent eval.

Playground

A model-comparison UI: pick a model (Claude, Gemini, Llama, gpt-oss-120b), paste a prompt, see the output. Cheap way to choose before committing.

Correction (transcript §playground). The lecturer referred to "GPT-OS 120 billion". The model's actual name is gpt-oss-120b, OpenAI's open-weight model (Apache 2.0), released August 2025. It runs on a single 80 GB GPU and is hosted in Databricks' Foundation Model API across AWS, Azure, and GCP — including in the Playground.

Databricks Apps

A managed app-hosting product inside Databricks itself. Good for lightweight internal tools that already need Unity Catalog auth and Genie. Not the place to host a public-facing customer app — the lecturer's guidance: "hosting, we will always go in a traditional way." Azure / AWS / GCP for production traffic, Databricks Apps for internal demos and tools.

The notebook coding assistant

A built-in agent in every Databricks notebook that takes natural-language prompts ("do an analysis on New York taxi data, create Plotly dashboard charts") and writes the code — SQL, Python, or PySpark, your pick. Comparable to GitHub Copilot Cloud, with the advantage that it already knows the schema of every table you can see in Unity Catalog. The lecturer's word of caution: "junior engineers are the happiest ones. They just write anything that the AI is telling and then share the code. Every day, 1,000-line, 2,000-line code. Most of the time you will just spend in debugging."

09 · COST & ACCESS

Cost and access

  • Free tier: ~40 credits or two months on sign-up, "enough to try and test everything."
  • Pay-as-you-go after that. Storage is billed even when idle — the lecturer pays monthly for data she "forgot to delete." Rule: delete or pay.
  • Marketplace install. Enable Databricks from your Azure / AWS / GCP marketplace; the workspace lives in your cloud account.
  • Account isolation. A second laptop with a different email gets a fresh free trial — useful for cohort experiments, not a long-term strategy.

Glossary

AgentBricks
Databricks' enterprise governance + deployment platform for agents. Supports LangGraph, LangChain, LlamaIndex, OpenAI Agents SDK as the authoring layer; adds Unity Catalog access control, MLflow CLEARS eval, Supervisor Agent orchestration, and one-step deploy to Databricks Apps.
AI/BI Dashboard
Databricks' Power-BI-style dashboard product with Genie embedded for ad-hoc questions.
Apache Spark
Distributed execution engine for large-scale data processing. Created at UC Berkeley AMPLab (2009); Databricks (founded 2013) commercializes it.
Catalog
Top-level Unity Catalog namespace; usually one per business unit or major project.
Databricks
Unified analytics platform combining managed Spark, Unity Catalog, MLflow, AI/BI Dashboards, Agent Bricks, and Lakebase. Cloud-only; available from Azure / AWS / GCP marketplaces.
Data dictionary
Column-by-column human-readable description of a table's schema. The single most important Genie input.
Delta Lake
The default table format in Databricks. Provides ACID transactions on top of cloud object storage.
Distributed processing
Partition the data and the logic across many machines, aggregate results. Fits SQL, streaming, classical ML; doesn't fit dense neural-network training well.
Genie
Databricks' first-party text-to-SQL agent. Takes a natural-language prompt + Genie Space, returns SQL + result table + chart + explanation.
Genie Conversation API
The REST endpoints (POST /api/2.0/genie/spaces/{space_id}/start-conversation and friends) that let external apps drive Genie programmatically.
Genie Space
The curated bundle (selected tables, column descriptions, hidden columns, general instructions, joins, saved SQL) that scopes one Genie deployment.
Hadoop
HDFS (distributed filesystem) + MapReduce (job framework), 2006. Not the same project as Spark, though they often run together.
Lakebase
Databricks' fully-managed serverless Postgres (powered by Neon), Public Preview June 2025, GA February 2026. The OLTP/operational store; complement to Delta tables (the OLAP/analytical store). Copy-on-write branching for agent sandboxes.
MLflow
Open-source experiment tracking, model registry, model serving, and evaluation framework. Maintained by Databricks; central to Agent Bricks' CLEARS scores.
Medallion architecture
Bronze (raw) / silver (cleaned) / gold (consumer-ready) layered transformation pipeline.
Parallel processing
Many cores in one machine acting on slices of one data structure. Fits dense neural-network training.
Planner agent
The first stage of Genie's two-step pipeline: decompose the natural-language question into ordered subtasks before generating SQL.
Schema
Second Unity Catalog level; usually one per project inside a catalog.
Supervisor Agent
Agent Bricks' orchestration pattern for routing tasks across multiple sub-agents and tools in one workflow.
Table
Structured data (rows + columns) in a schema. Backed by Delta Lake by default.
Unity Catalog
Databricks' unified governance layer over data, models, files, and tools. Enforces access control, lineage, and discovery at the storage layer.
Volume
Unstructured-file storage inside a schema (PDFs, images, raw text). Use Volumes for RAG document corpora.
