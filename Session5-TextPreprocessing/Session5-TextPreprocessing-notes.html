SESSION 05 · STUDY NOTES · NLP PREREQUISITES

Cleaning text before it can be a number.

Lowercase, tokenize, stem or lemmatize, drop stopwords — the classical pipeline that prepares text for embedding. Plus what modern LLMs do instead.

PREREQUISITE FOR S6+S7 NLTK / SPACY 4-STEP PIPELINE
WHERE WE ARE

Sessions 3-4 covered the training loop on numerical data: a perceptron with weights, a loss, gradient descent. That whole machinery assumes the input is already a number. For images this is easy — every pixel is a number — but text is just text, and a math model can't multiply "the phone is good" by a weight matrix.

This session is the plumbing that turns raw text into something a model can train on. We don't build a model. We don't even produce numbers yet (that's Session 6, embedding). What we do is clean the text — lowercase, tokenize, lemmatize, drop stopwords — so that when we convert to numbers in the next session, we're not multiplying redundant or noisy inputs.

Next session (Session 6): embedding. Take the cleaned text from today and turn each token into a vector of numbers. After that we're set up for the Transformer encoder (Session 7+).

Classical NLP preprocessing — lowercase, tokenize, stem/lemmatize, remove stopwords — exists to shrink the feature space before a model trains on it. Modern Transformer LLMs skip most of this because subword tokenizers handle the same problems differently. We're learning the classical pipeline because it's still relevant for traditional ML, interviews, and as background for the Transformer encoder.
§ 01 — THE GAP

Why text needs preprocessing

Every algorithm we've seen so far computes on numbers. The perceptron multiplies weights by inputs (numbers); gradient descent takes derivatives of a loss (a number); even the activation functions (ReLU, sigmoid, softmax) all map numbers to numbers. There is no point in the training loop where a string of letters could appear.

Two kinds of data fit naturally:

  • Structured data — rows and columns of numbers (a CSV of house prices, a database table). Already numeric.
  • Images — each pixel is a triple of integers (R, G, B values in 0–255). Already numeric.

Text is the odd one out:

  • Unstructured data — paragraphs, sentences, comments, transcripts. Not numeric.

So we need a process to convert text into numbers before any model can touch it. That process has two halves:

  1. Preprocessing (this session) — clean up the text so we're not converting redundant or meaningless pieces.
  2. Embedding (Session 6) — actually turn each cleaned piece into a numeric vector.

§ 03 — DESTINATION

What "embedding" means (preview)

Embedding = converting text into numbers. Specifically: a function embed: text → vector_of_floats that preserves meaning — words with similar meanings get similar vectors.

The history, very briefly:

  • 2010s early — count-vectorizer (just count word frequencies), TF-IDF (frequency weighted by rarity). Fast but no notion of meaning.
  • 2013 — Word2Vec (Mikolov et al.). First widely-used embedding that captured semantic similarity. "king" and "queen" end up near each other in vector space.
  • 2014 — GloVe (Pennington et al.). Similar idea, different training objective.
  • 2018 — BERT (Devlin et al.). First Transformer-based embedding; same word gets different vectors in different contexts.
  • 2019+ — every modern LLM (GPT, Llama, Claude) has its own embedding layer as the first step.

We'll cover Word2Vec in Session 6 to understand the foundational ideas, then jump to the Transformer encoder in Session 7. The lecturer summarised: "The entire encoder block of Transformer is embedding only." Useful slogan — the encoder's job is to produce a final, context-aware embedding of the input that the decoder can then work with.

Correction — "Word2Vec was the only algorithm in 2018-19."

Word2Vec was published in 2013 and was widely used through 2016-17. By 2018, BERT had been published and was already displacing Word2Vec for serious NLP work. The "only algorithm" framing is a decade off. Word2Vec is taught because it's foundational — it's the cleanest illustration of how a learned vector can carry meaning — but it's not the state of the art and hasn't been for years.

§ 05 — WHY CLEAN

Feature engineering for text

The lecturer's working example:

WORKED EXAMPLE

Input: "the phone is good"

Task: classify sentiment (positive / negative)

Are all four words equally informative? Obviously not. "good" carries almost all the signal; "the", "is" are functional words that appear in millions of sentences, positive or negative.

Feature engineering for text means: identify and keep the words that carry signal; identify and drop the ones that don't. This isn't just aesthetics — it's mathematically load-bearing:

  • Fewer features → faster training. Each unique word becomes a column (or a dimension) in the model's input space. Dropping noise shrinks the search space.
  • Less noise → better generalisation. A model trained on "good" vs "bad" as the signal will outperform one that also has to learn "the doesn't matter," because the latter has more chances to overfit.
  • Cheaper to serve. Smaller vocabularies → smaller embedding tables → less memory and faster inference.
Correction — feature engineering is much less important for Transformer LLMs.

Modern models like GPT-4 or Llama 3 do almost no feature engineering — they take raw text, run it through a subword tokenizer, and let the network learn what matters. The four-step pipeline below is essential for the classical era (logistic regression + TF-IDF) and still useful for some traditional NLP tasks, but you shouldn't apply it before feeding text to a modern LLM. We'll see the LLM pipeline in Session 7+.

§ 06 — THE PIPELINE

The classical 4-step pipeline

Step 1 — Lowercase

text.lower(). One line of Python.

Why: the model treats "Phone" and "phone" as two different words unless you collapse them. A vocabulary that distinguishes them by capitalisation alone is bloated for no reason.

Correction — lowercasing destroys named-entity signal.

"Apple" the company and "apple" the fruit are genuinely different words. "Polish" (a nationality, capital P) and "polish" (a verb, lowercase) are different. Lowercasing throws this signal away. For sentiment analysis on consumer reviews it doesn't matter much; for NER, translation, or any task that depends on entities, it's harmful. BERT ships in two variants — bert-base-uncased (lowercased) and bert-base-cased (preserves case) — precisely because the right choice depends on the task. Don't lowercase by reflex.

Step 2 — Tokenization

Split the text into tokens — the smallest units the model will treat as atomic.

Word-level tokenization (the lecturer's default): split on whitespace + punctuation. "the quick brown fox" → ["the", "quick", "brown", "fox"].

Sentence-level tokenization: split on sentence boundaries. "Hello world. Goodbye world." → ["Hello world.", "Goodbye world."].

NLTK gives you both via word_tokenize and sent_tokenize. The right level depends on what your model needs.

What is a "token," precisely?

A token is a logical atomic unit. Word and sentence are two coarse-grained choices. Modern LLMs use a finer unit called a subword token:

"preprocessing" → ["pre", "process", "##ing"]   (BERT WordPiece tokenizer)
"unbelievable"  → ["un", "bel", "iev", "able"]  (a BPE tokenizer)

Why subwords? Three reasons:

  1. Bounded vocabulary. English has millions of distinct words (especially counting names, typos, hashtags); a subword vocabulary of 32K-50K pieces covers all of them.
  2. Handles unknown words. "covfefe" isn't in any word vocabulary. With subword tokenization it becomes some sequence of letter-pieces.
  3. Captures morphology. "running" and "ran" share root tokens, so the model gets a hint they're related.

The three dominant subword algorithms are BPE (Byte Pair Encoding, Sennrich et al. 2016 — used by GPT-2/3/4), WordPiece (Devlin et al. 2018 — used by BERT), and SentencePiece (Kudo & Richardson 2018 — used by Llama, Gemma, T5).

Correction — "tokens per minute" billing isn't about word-tokens.

When OpenAI bills you for "1 million tokens per request," they mean the model's subword tokens, computed by the model's specific tokenizer. English text averages roughly 1.3 GPT-tokens per word, but it varies — code and non-English languages tokenize to more tokens per character. You can compute exact counts with OpenAI's tiktoken library before sending the request, which is good practice when costs matter.

JAVA/SPRING BRIDGE

Tokenization ≈ a Lexer. If you've written a parser with ANTLR, or dug into how javac processes source code, the first phase is the lexer: turn a flat character stream into a stream of structured tokens (identifiers, keywords, operators). NLP tokenization is the same idea — the units are words instead of programming-language keywords, but the role is identical: hand the next phase (parser, or in our case, the model) a clean stream of atoms.

Step 3 — Stemming OR Lemmatization

Both do the same job: reduce inflected forms of a word to a single root form, so the model sees "run", "runs", "running", "ran" as the same underlying concept.

You pick one. Not both.

Stemming (the fast, dumb one)

Stemming strips suffixes by rule. The most common algorithm is Porter Stemmer (Porter 1980), which applies a sequence of suffix-rewriting rules:

"running" → "run"     (strip -ing)
"foxes"   → "fox"     (strip -es)
"happily" → "happili" (strip -y, replace with -i — can produce non-words)
"lazy"    → "lazi"    (same rule)

The lecturer demonstrated Porter Stemmer producing "lazi" from "lazy". That's the trade-off — sometimes the "stem" isn't a real word. It doesn't matter for the model (which treats "lazi" as just another token), but it makes debugging output less readable.

Speed: very fast. Pure string manipulation, no lookups.

Lemmatization (the slow, smart one)

Lemmatization uses a dictionary to look up the canonical "lemma" of a word, optionally informed by the word's part of speech.

"running" (verb) → "run"
"better"  (adj.) → "good"        (← stemming can't do this; dictionary entry)
"was"     (verb) → "be"
"foxes"   (noun) → "fox"
"lazy"    (adj.) → "lazy"        (← already a lemma; not mutilated)

NLTK provides this via the WordNet Lemmatizer. WordNet (Princeton, 1985–) is a large lexical database of English; the lemmatizer just looks each word up.

Speed: much slower than stemming — dictionary lookups and POS-tagging overhead.

When to use which

Use casePick
Massive corpus, classification task, accuracy isn't criticalStemming (Porter / Snowball). Speed wins.
Smaller corpus, chatbot / QA / customer-facing task, output read by humansLemmatization. Accuracy and real-word output win.
Correction — the lemmatizer doesn't do NER.

The transcript mentioned that WordNet Lemmatizer "does NER, named entity recognition." It doesn't. The lemmatizer uses POS tags (part-of-speech: noun, verb, adjective, adverb) to disambiguate the right lemma ("better" as an adverb → "well"; as an adjective → "good"). NER is a separate task — finding people, places, organisations — handled by different tools (spaCy's ner pipeline, HuggingFace's dslim/bert-base-NER, etc.). The lecturer conflated POS tagging with NER; they're related (both label tokens with metadata) but distinct.

Correction — "the math model will understand" frames the right thing the wrong way.

When the lecturer said "lazy → lazi is fine, model will understand," she's correct in context — the model just sees "lazi" as another token ID and doesn't care that it's not a real word. But beginners hearing this often interpret it as "the model has some understanding of English." It doesn't. It has learned statistical regularities over token IDs. "lazi" works only because it's consistently used as the stem for both "lazy" and "lazier" — the consistency is what the model exploits, not the linguistic meaning.

JAVA/SPRING BRIDGE

Stemming vs lemmatization ≈ regex strip vs ElasticSearch analyzer. Porter Stemmer is like a sequence of String.replaceAll(suffix, "") calls — fast, ruthless, occasionally garbles input. WordNet Lemmatizer is like an ElasticSearch analyzer with a synonym mapping plus part-of-speech context — slower but produces canonical forms a human would recognise.

Step 4 — Stopword removal

Stopwords are the high-frequency, low-information words in a language: "the", "is", "are", "a", "and", "of", "to", "in", … In English they're a closed set of about 150 words.

from nltk.corpus import stopwords
stop = set(stopwords.words("english"))
clean = [tok for tok in tokens if tok not in stop]

Why: they appear in every sentence, positive or negative, so they carry essentially no signal for tasks like sentiment classification. Drop them, the vocabulary shrinks, the signal-to-noise ratio improves.

Correction — stopwords can carry signal for some tasks.

In sentiment classification you can drop them safely. In negation handling you cannot — "the phone is not good" reverses sentiment, and "not" is sometimes treated as a stopword. Check your stopword list before applying it to a task that depends on negation, modal verbs, or grammatical structure. Modern Transformer models don't drop stopwords at all — they let the attention mechanism learn which words to pay attention to per context.

JAVA/SPRING BRIDGE

Stopword removal ≈ a deny-list Filter in a Spring FilterChain. Same shape: a list of patterns; anything matching gets dropped before downstream processing sees it.

§ 07 — TERMINOLOGY

Vocabulary vs corpus

The lecturer used "corpus" to mean "the set of unique words left after cleaning." That's not the standard usage. Quick disambiguation:

TermStandard NLP meaning
CorpusThe whole collection of documents / text you're working with. "My corpus is 10,000 Reddit comments."
VocabularyThe set of unique tokens that appear in your corpus. "My vocabulary has 8,200 unique tokens after preprocessing."
TokenA single occurrence of a unit (word or subword) in the text. "This document has 540 tokens."
TypeA unique token; another word for vocabulary entry. "540 tokens but only 230 types."

So if she said "my corpus is 20,000 words," she meant "my vocabulary is 20,000 words" by standard NLP usage. The corpus would be the document collection that contains those 20,000 unique words. Both senses are intelligible in context, but interview-precise usage matters.

§ 08 — THE BIGGER PICTURE

What modern LLMs actually do

Here's the side-by-side that explains why the lecturer's GenAI/Agentic-AI course doesn't dwell on this pipeline:

StepClassical NLPModern LLM
LowercaseYes, almost alwaysUsually no (cased models preserve case)
TokenizeWord-level (split on space)Subword (BPE / WordPiece / SentencePiece)
Stem / LemmatizeOne of the two, almost alwaysNo
Stopword removalYes, almost alwaysNo
What replaces all this?n/a — this is the pipelineSubword tokenizer + the attention mechanism

The shift happened around 2017 (the Transformer paper) and was complete by 2019 (BERT, GPT-2). Modern LLMs use subword tokenization on raw text and let the network learn which tokens matter. The "feature engineering" of dropping stopwords or normalising case is implicit in what the attention layers learn.

Why are we still teaching it then? Three reasons:

  1. Traditional NLP is still used. Sentiment classifiers built on TF-IDF + logistic regression are fast, interpretable, and good enough for many production tasks. They need this pipeline.
  2. Fine-tuning a domain model. If you're fine-tuning a smaller model on your own domain data, you may still want to do some cleaning (de-duplication, removing boilerplate) — not the four steps above, but the spirit of "remove redundancy before training."
  3. Interviews. "Explain stemming vs lemmatization" is a near-guaranteed question.

For everything else — building agents on top of pre-trained LLMs, calling APIs, RAG pipelines — feed the model raw text and let it do its own tokenization.

§ 09 — CODE

Putting it together: one Python walkthrough

The lecturer's full NLTK pipeline as it appears in code, annotated:

import nltk
from nltk.tokenize import word_tokenize
from nltk.stem import PorterStemmer, WordNetLemmatizer
from nltk.corpus import stopwords

text = "The quick brown foxes ARE jumping over the lazy dogs!"

# Step 1: lowercase
text = text.lower()
# → "the quick brown foxes are jumping over the lazy dogs!"

# Step 2: tokenize (word-level)
tokens = word_tokenize(text)
# → ["the", "quick", "brown", "foxes", "are", "jumping",
#    "over", "the", "lazy", "dogs", "!"]

# Step 3a: stem (pick one of 3a OR 3b — fast and dumb)
stemmer = PorterStemmer()
stemmed = [stemmer.stem(t) for t in tokens]
# → ["the", "quick", "brown", "fox", "are", "jump",
#    "over", "the", "lazi", "dog", "!"]

# Step 3b: lemmatize (pick one of 3a OR 3b — slow and smart)
lemmatizer = WordNetLemmatizer()
lemmas = [lemmatizer.lemmatize(t) for t in tokens]
# → ["the", "quick", "brown", "fox", "are", "jumping",
#    "over", "the", "lazy", "dog", "!"]
# Note: "jumping" stayed because lemmatize defaults to noun POS;
# pass pos="v" to lemmatise verbs properly.

# Step 4: remove stopwords + punctuation
stop = set(stopwords.words("english"))
final = [t for t in lemmas if t not in stop and t.isalpha()]
# → ["quick", "brown", "fox", "jumping", "lazy", "dog"]

Six clean tokens out the other side. Those are the units that go into Session 6's embedding step.

§ NEXT — SESSION 06

For Session 6

Tomorrow's topic is embedding — taking each cleaned token and turning it into a vector of floats that captures meaning.

The plan the lecturer outlined:

  1. CountVectorizer — the dumbest possible embedding: each token becomes a column, value is the count of how often it appears. Sparse, no notion of meaning.
  2. Word2Vec (Mikolov 2013) — a learned dense embedding. Similar words end up with similar vectors. This is where "king − man + woman ≈ queen" comes from.
  3. Transformer encoder embeddings — context-aware. "bank" in "river bank" and "bank" in "investment bank" get different vectors. Session 7 covers this from the encoder angle; we'll meet it again from the embedding angle.

What to remember from today, going into Session 6:

  • The preprocessing pipeline produces a sequence of cleaned tokens, not numbers yet.
  • Embedding is the step that converts tokens → vectors.
  • The full pipeline for a classical NLP project is: preprocess → embed → train → validate → deploy.
  • Modern LLMs collapse "preprocess + embed" into "subword tokenize + learned embedding layer," all inside the model.
INTERVIEW-READY SUMMARY

"Classical NLP preprocessing has four steps: lowercase, tokenize, stem or lemmatize, drop stopwords. The point is feature-space reduction before training a traditional model like TF-IDF + logistic regression. Modern Transformer LLMs skip most of this — they use subword tokenization (BPE for GPT, WordPiece for BERT, SentencePiece for Llama) on raw text and let the network learn what matters. Stemming is fast and rule-based (Porter); lemmatization is slow and dictionary-based (WordNet). NLTK is the teaching library; spaCy is the production library."

Glossary

BPE (Byte Pair Encoding)
Subword tokenization algorithm used by GPT-2/3/4. Iteratively merges most-frequent character pairs to build a vocabulary of ~50K subwords.
Corpus
A collection of documents or text used for analysis or training. Not the same as vocabulary.
Embedding
A function mapping text (or a token) to a vector of floats, ideally preserving meaning.
Feature engineering
The practice of selecting and transforming the input variables a model sees, to improve its performance.
Lemma
The canonical dictionary form of a word. "Run" is the lemma of "running", "ran", "runs".
Lemmatization
Reducing a word to its lemma using a dictionary + POS context.
NER (Named Entity Recognition)
Identifying named entities (people, places, organisations, dates) in text. Separate from POS tagging and from lemmatization.
NLTK / Gensim / spaCy
The three main Python classical-NLP libraries. NLTK = teaching, Gensim = topic modeling, spaCy = production.
POS (Part of Speech)
A grammatical category: noun, verb, adjective, adverb, etc. Used as input to lemmatization for disambiguation.
Porter Stemmer
A widely-used suffix-stripping stemming algorithm (Porter 1980).
Pre-trained model
A model someone else trained, that you download and use (possibly fine-tune) instead of training from scratch.
SentencePiece
Subword tokenization library used by Llama, Gemma, T5. Treats input as raw bytes, handles any language.
Stemming
Reducing a word to a "stem" by stripping suffixes. Fast, may produce non-words.
Stopword
A high-frequency, low-information word like "the", "is", "and". Often removed in classical NLP preprocessing.
Subword tokenization
Tokenization at a finer granularity than words. "preprocessing" → ["pre", "process", "##ing"]. Used by all modern LLMs.
TF-IDF (Term Frequency – Inverse Document Frequency)
A classical text-representation scheme that weights words by frequency in the document divided by frequency across all documents.
Token
A single unit produced by tokenization. Can be a word, subword, or character.
Tokenization
Splitting text into tokens.
Type
A unique token (a vocabulary entry). "The cat sat on the mat" has 6 tokens but 5 types ("the" appears twice).
Vocabulary
The set of unique tokens (types) used by a model or in a corpus.
Word2Vec
A foundational learned embedding (Mikolov 2013). First widely-used method to capture semantic similarity between words.
WordPiece
Subword tokenization algorithm used by BERT. Similar to BPE.
WordNet
A large lexical database of English (Princeton, 1985–). Used by NLTK's lemmatizer for dictionary lookups.
