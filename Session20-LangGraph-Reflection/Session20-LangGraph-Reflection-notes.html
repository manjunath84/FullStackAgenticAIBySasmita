WHERE WE ARE

Session 19 was the LangGraph foundation: state, nodes, edges, conditional edges, and a hand-built ReAct loop. Session 20 reuses those primitives to build two more patterns and shows you the prebuilt helper for the most common one. No new primitives — what's new is the shape of the graph you wire from them. Session 21 will add interrupts and checkpointed memory so a human can review and edit between nodes.

The four primitives don't change. What changes is the shape of the graph — reflection layers a critic over a draft; routing fans out by classification; ReAct loops between model and tools. Pattern is geometry.
§ 01 — RE-FOUNDATION

The four primitives, one minute

The lecturer opened with a tight recap of Session 19. If any of this feels new, go back to Session 19 §2 — the rest of this note assumes it.

PrimitiveOne-line definition
StateA TypedDict shared across every node. Every node reads it; every node returns a partial dict that LangGraph merges back in.
NodeA function state → dict. Inside it you can call an LLM, run a tool, do plain Python — anything.
Edge"After A, always run B." Fixed routing. graph.add_edge("A", "B").
Conditional edge"After A, look at state (via a small router function) and pick B or C or D." graph.add_conditional_edges("A", router_fn, {...}).
START / ENDMarkers for entry and exit. Not nodes you write.

The build sequence is always the same: StateGraph(SchemaClass) → add_node(...) × N → add_edge(...) / add_conditional_edges(...) × M → compile() → invoke(state_dict).

JAVA / SPRING BRIDGE

StateGraph(...).compile() is the analogue of ApplicationContext refresh: you wire the beans (nodes), declare how they're connected (edges), and call refresh() (compile) once. After that, invoke(...) is just a method call on the assembled object — you don't re-wire on every request.

WHERE THE BRIDGE BREAKS

Spring's bean graph is a static dependency graph resolved once at startup. LangGraph's graph executes: nodes run in sequence (or branch / loop) every time you call invoke. The graph object is the program, not the wiring diagram.

§ 02 — REFLECTION PATTERN

Draft, critique, revise

2.1 The idea

The lecturer's framing: take an LLM's first output, hand it to a second LLM acting as a critic, and let the critic either approve it (go to END) or request changes (run a revise step, then END). It's a useful pattern when the work is generation — writing prose, summarising, drafting a blog post, producing structured output — and you'd like a second pass for quality.

WHAT THIS IS CALLED IN THE LITERATURE

"LLM-as-judge" or "LLM-as-critic." The clearest survey is Zheng et al. 2023, Judging LLM-as-a-Judge with MT-Bench and Chatbot Arena (arXiv:2306.05685). The reflection-style multi-step variant traces back to Madaan et al. 2023, Self-Refine: Iterative Refinement with Self-Feedback (arXiv:2303.17651). LangGraph is just the orchestration; the pattern is independent of it.

2.2 The state

Three keys: the topic, the current draft, the critic's notes. draft and critique both get written during the run — the caller passes empty strings.

from typing import Literal, TypedDict

class ReflectState(TypedDict):
    topic: str
    draft: str
    critique: str

2.3 The three nodes

Draft node. First LLM call. Writes a short answer to the topic.

def write_draft(state: ReflectState) -> dict:
    r = llm.invoke([HumanMessage(
        content=f"Write a 3-sentence answer about: {state['topic']}"
    )])
    return {"draft": r.content}

Critique node. Second LLM call. Reads the draft and produces bullets. The prompt deliberately asks for the word IMPROVE if changes are needed — that sentinel is what the conditional edge will look for.

def critique_draft(state: ReflectState) -> dict:
    r = llm.invoke([HumanMessage(content=(
        f"Critique this answer briefly (bullets). "
        f"Say IMPROVE if it needs work.\n\n"
        f"{state['draft']}"
    ))])
    return {"critique": r.content}

Revise node. Third LLM call. Rewrites the draft given the critique. Writes back to the draft key so the final state ends up with the improved version.

def revise(state: ReflectState) -> dict:
    r = llm.invoke([HumanMessage(content=(
        f"Improve the draft using the critique. Keep 3 sentences.\n"
        f"Draft:\n{state['draft']}\n\nCritique:\n{state['critique']}"
    ))])
    return {"draft": r.content}

2.4 The conditional edge

The only "smart" part. The router function reads the critique and returns one of two literal strings:

def after_critique(state: ReflectState) -> Literal["revise", "__end__"]:
    if "IMPROVE" in state["critique"].upper():
        return "revise"
    return END
WHY THE "IMPROVE" SENTINEL?

The router function has to make a routing decision from data already in state. Asking the critic LLM to say a specific keyword if changes are needed gives you a cheap, deterministic substring check in the router. It's a trick, not a requirement — alternatives include adding a boolean needs_revision field to state, or asking the critic for structured JSON. The sentinel is the shortest path for a teaching example.

JAVA / SPRING BRIDGE

The router function is a strategy resolver. Conceptually the same shape as Spring's @Conditional resolving at startup, except this one resolves on every invocation and the input is mutable state, not a static Environment.

2.5 Wiring it up

from langgraph.graph import END, START, StateGraph

fb = StateGraph(ReflectState)
fb.add_node("draft", write_draft)
fb.add_node("critique", critique_draft)
fb.add_node("revise", revise)

fb.add_edge(START, "draft")
fb.add_edge("draft", "critique")
fb.add_conditional_edges(
    "critique",
    after_critique,
    {"revise": "revise", END: END},
)
fb.add_edge("revise", END)

reflect_app = fb.compile()

final_state = reflect_app.invoke(
    {"topic": "Why use graphs for agents?", "draft": "", "critique": ""}
)

Three things to notice. First, the conditional-edges call takes a mapping {router_return_value: next_node} — the router can return any string; the mapping translates it to a node name. Second, the conditional edge sits on the critique node, not on revise — the branch is "after critique, decide." Third, START → draft and draft → critique are plain add_edge. You only reach for add_conditional_edges where the graph actually branches.

2.6 One revision pass — and a sharper claim than the lecturer made

In the diagram above, revise → END is unconditional. So even if the revised draft is still bad, you exit. To get multiple passes you'd point revise → critique instead, making it a loop, and let the critique decide when to stop.

The lecturer warned: "If you use the same LLM for draft and critic and revise, repeated passes won't improve anything — it's the same machine thinking the same way."

Sharpened claim. That's partially right but stated too strongly. Three reasons repeated passes with one model can improve output: (1) the prompts are different — "write a draft" and "critique this draft" induce different behaviour from the same weights; (2) sampling is non-deterministic — at temperature > 0 the same model on the same prompt produces different tokens on different calls; (3) the Self-Refine paper (Madaan et al. 2023) reports gains on most tasks using a single model for generate / feedback / refine, across GPT-3.5 and GPT-4. Gains plateau after a couple of iterations and on some tasks actively hurt. The lecturer's practice advice — if you're going to iterate, use a different model for the critic — is good. The implicit claim that one-model iteration is useless is too strong.

2.7 The lecturer's "you can loop it" extension

A student asked: what if I want the critic to keep asking for improvements until it's satisfied? The answer is to repoint revise → critique instead of revise → END. That turns the linear "one pass" graph into a ReAct-shaped loop — critique is now the gating node, like the LLM in last week's ReAct.

Correction (lecturer's quick aside). The lecturer said you can set the iteration count "in the prompt only" by writing "repeat 3 times." That doesn't reliably stop an LLM loop — prompt instructions about counting are routinely ignored. The correct way to bound iteration is in code: add an iteration: int field to state, increment it in revise, and have the router return END once it exceeds your cap.
§ 03 — PREBUILT REACT

Last week's hand-built loop, in one line

Session 19 walked through building a ReAct loop by hand: an agent node calling an LLM bound to tools, a ToolNode running the tool calls, a conditional edge sending the flow back to the agent if there are more tool calls, or to END otherwise. That code is correct and worth understanding once.

You won't write it again. LangGraph ships a prebuilt helper:

from langgraph.prebuilt import create_react_agent
from langchain_core.tools import tool

@tool
def word_count(text: str) -> int:
    """Count words in a string."""
    return len(text.split())

prebuilt = create_react_agent(llm, [word_count])

out = prebuilt.invoke({
    "messages": [HumanMessage(
        content="How many words in: LangGraph makes agents easier?"
    )]
})
print(out["messages"][-1].content)

That's the whole agent. The function builds the LLM-↔-ToolNode subgraph for you, wires the conditional edge, and returns a compiled graph you can invoke on.

JAVA / SPRING BRIDGE

Hand-wiring the ReAct loop is @Configuration with explicit @Bean methods. create_react_agent is Spring Boot auto-configuration — you trade some flexibility for the common case wired correctly out of the box. Reach for the prebuilt by default; drop down to hand-wired when you need a non-standard variant (e.g., reflection on top of tool calls, a custom retry policy, or branches we'll see in Session 21).

REACT = REASON + ACT

One name-collision worth nailing once: ReAct here means Reason + Act (Yao et al. 2022, arXiv:2210.03629), not the JavaScript UI library. The transcript's "React, reason, and act" phrasing is muddled; the term is a contraction of Reason and Act.

The lecturer's framing: "Many of the times you may need React more than Reflection because React is very helpful for tool calls." That's accurate — most agentic workloads are "let the model call tools to gather information," not "let the model rewrite its own prose."

§ 04 — CONDITIONAL ROUTING

Customer-service worked example

This is the same primitive as the reflection branch, applied to a different shape: classify an inbound request, route it to one of several handler nodes, each handler does its own thing. It's the canonical use case for add_conditional_edges.

4.1 The state

from typing import TypedDict, Literal
from langgraph.graph import END, START, StateGraph

class SupportRequest(TypedDict):
    message: str      # the customer's message
    priority: int     # 1 = high, 3+ = low
    status: str       # routing status — written by nodes as they run

The status field is a stand-in for "downstream nodes can see where the request has been." In real life you'd carry an assigned team, an SLA timestamp, ticket IDs — anything you'd otherwise stuff into a request-scoped Spring bean.

4.2 The first node: classify, then update status

def categorize_request(request: SupportRequest):
    """Initial node that receives and logs the request"""
    print(f"📥 Received request: '{request['message']}'")
    print(f"   Priority Level: {request['priority']}")
    return {"status": "categorized"}

In this teaching example the node doesn't actually classify anything — it just stamps status = "categorized" and prints. The real classifier is the router function below, which reads priority straight from state. We'll come back to "but what if priority isn't given?" in §4.6.

4.3 The router function (this is the conditional edge)

def route_by_priority(
    request: SupportRequest,
) -> Literal["handle_urgent", "handle_standard"]:
    if request["priority"] <= 2:
        return "handle_urgent"
    return "handle_standard"

Two things to notice. The return type is Literal[...] — a hint to readers and to LangGraph that this function always returns one of a fixed set of strings. And the function takes state as input, the same as any node. A router function is a node-shaped object that returns a routing decision instead of a state update.

4.4 The handler nodes

def handle_urgent(request: SupportRequest):
    print(f"🔴 URGENT processing: '{request['message']}'")
    return {"status": "urgent_handled"}

def handle_standard(request: SupportRequest):
    print(f"🟢 STANDARD processing: '{request['message']}'")
    return {"status": "standard_handled"}

In this demo they only update status. In reality you'd send the email, page the on-call, file the ticket, write to a database — whatever the workload requires.

4.5 Wiring it up

graph = StateGraph(SupportRequest)

graph.add_node("categorize_request", categorize_request)
graph.add_node("handle_urgent",      handle_urgent)
graph.add_node("handle_standard",    handle_standard)

graph.add_edge(START, "categorize_request")
graph.add_conditional_edges(
    "categorize_request",
    route_by_priority,
    {"handle_urgent": "handle_urgent",
     "handle_standard": "handle_standard"},
)
graph.add_edge("handle_urgent",   END)
graph.add_edge("handle_standard", END)

runnable = graph.compile()

result = runnable.invoke({
    "message": "My account was hacked! Urgent help needed.",
    "priority": 1,
    "status": "new",
})

Fig 2 above is exactly this graph rendered from the compiled runnable via runnable.get_graph().draw_mermaid_png(). The dashed edges out of categorize_request are LangGraph's convention for conditional edges; the solid edges into END are plain.

4.6 "But what if priority isn't given?"

In the code above, the caller has to know to pass priority: 1. That's fine for a unit test, but in production the customer just types a message — they don't tag it with a priority level.

The lecturer's fix (and it's the right one): make categorize_request an actual LLM call. Read message, ask the model "rate this 1 (urgent) to 5 (routine) and reply with just the number," parse the answer, write it back to state["priority"]. Downstream the router function doesn't change — it still reads priority from state.

def categorize_request(request: SupportRequest):
    r = llm.invoke([HumanMessage(content=(
        f"On a scale of 1 (urgent) to 5 (routine), rate this "
        f"customer message. Reply with just the integer.\n\n"
        f"Message: {request['message']}"
    ))])
    try:
        priority = int(r.content.strip())
    except ValueError:
        priority = 3  # fallback to standard
    return {"priority": priority, "status": "categorized"}
STUDENT POINT — WORTH PRESERVING

One student raised the right concern: "the user can lie about their own priority." Exactly — which is why an LLM classifier reading the message is more trustworthy than a self-reported integer. Both can be wrong; the LLM is wrong in less manipulable ways.

4.7 "But isn't this just an if/else?"

Krishna Chaitanya pushed back: the example uses one LLM, the routing is a simple comparison — what does LangGraph add over a Python if? The transcript's answer was scattered. The clear version has four parts:

  1. The branch decision can itself be an LLM call. Once categorize_request becomes the LLM classifier in §4.6, the "if priority ≤ 2" gate is reading a value that an LLM just produced. That's not a static if/else — the routing is decided by a model every time.
  2. State is shared across nodes. Each node sees and updates the same SupportRequest. In a flat function you'd thread that as parameters. In a longer pipeline (10+ nodes, some looping, some branching) you'd reinvent state-passing badly. LangGraph gives you that for free.
  3. Loops aren't expressible in flat if/else. ReAct's "LLM → tool → LLM → tool …" cycle isn't a switch statement; it's a graph with a back-edge. The same conditional-edges API supports both shapes.
  4. Checkpointing comes for free. Add a MemorySaver (next session) and any partial run can pause, persist, and resume. That's three lines of code in LangGraph; rolling it yourself on top of an if/else means writing serialisation, thread keys, restart logic.

If the example is small enough that an if/else handles it, an if/else is the right answer. LangGraph earns its keep when the graph is non-trivial or one of points 1, 3, or 4 applies.

4.8 Visualising the compiled graph

You don't have to draw the diagram by hand. After compile(), LangGraph can emit a Mermaid diagram and render it as PNG:

from IPython.display import Image, display
display(Image(runnable.get_graph().draw_mermaid_png()))

Fig 2 above was produced this way. For a static PDF version you'd save the Mermaid source (.get_graph().draw_mermaid()) and render it through any Mermaid renderer.

§ 05 — BIG-PICTURE CLARIFICATION

LangGraph is orchestration, not "an agent"

Late in the session the lecturer made a careful distinction that's easy to miss: LangGraph is not an agent. It's a framework for orchestrating agents. The actual agent — the LLM with a prompt and a tool list — is a LangChain object that lives inside a node. LangGraph decides which node runs when, what state they share, when to loop, when to stop.

LayerWhat it isConcrete thing
L1The modelAn LLM endpoint (OpenAI, Anthropic, Gemini, a local model).
L2The agentA LangChain object: prompt + LLM + tools + memory. One agent.
L3The orchestrationA LangGraph graph: nodes call agents (or tools, or functions); edges decide flow.

A LangGraph node can wrap an L2 agent, a plain Python function, a tool call, or another sub-graph. The graph doesn't care.

WHAT "MULTI-AGENT" ACTUALLY MEANS

The lecturer used "multi-agent" loosely throughout. The tight definition: a system where two or more LLM-driven components with distinct roles collaborate through shared state, often with different prompts, tools, or models. The reflection pattern above is multi-agent — drafter and critic are two roles, possibly two models. The customer-service example as written isn't multi-agent — it has one LLM (or none) plus deterministic handlers. Multi-agent isn't about how many LLM calls you make; it's about distinct roles with their own concerns.

5.1 "LangGraph is the best" — flag

The lecturer said LangGraph is "the best" multi-agent framework and you "don't need to learn anything else." Treat that as a strong opinion, not a fact. As of mid-2026 the live alternatives include:

§ 06 — NEXT SESSION PREVIEW

Human-in-the-loop coding assistant

The lecturer ended with a demo of next session's build: a graph that generates code, pauses for human review, and resumes with whatever the human decides. We won't walk the code here — that's Session 21's job — but here's the shape so the preview lands.

6.1 Two new primitives (Session 21)

PrimitiveWhat it does
interrupt(payload)Inside a node, pauses the graph. The caller's invoke(...) returns with an __interrupt__ key containing payload. Whoever is driving the run (a UI, a Slack bot, a notebook cell) shows the payload to a human and collects a response.
Command(resume=value)Re-invoke the compiled graph with Command(resume=value) instead of new input. LangGraph picks up where it paused; the interrupt() call returns value.

Both live in langgraph.types.

6.2 Why this needs a checkpointer

interrupt() only works if the graph can persist its state while paused. That's what a checkpointer does. The simplest one:

from langgraph.checkpoint.memory import MemorySaver
app = workflow.compile(checkpointer=MemorySaver())

MemorySaver keeps state in memory, which is fine for notebooks. For production you swap in PostgresSaver (also bundled) and the state survives process restarts. Every checkpointed run is keyed by a thread ID, passed in the config:

config = {"configurable": {"thread_id": "coding-session-001"}}
app.invoke(inputs, config=config)
# ... later, possibly after a process restart ...
app.invoke(Command(resume={"action": "approve"}), config=config)
JAVA / SPRING BRIDGE

thread_id + checkpointer ≈ Spring Session. Same session ID → same state restored, regardless of which process picks up the next request. MemorySaver is the in-memory session store; PostgresSaver is the JDBC-backed one.

§ 07 — RECAP

What to take into Session 21

You should walk out of this class able to do four things without thinking:

  1. State first. When sketching any new LangGraph workflow, design the TypedDict before you write a node. The fields are your contract.
  2. add_edge for straight runs, add_conditional_edges at branches. Branch decisions live in a small router function that returns a literal string keyed to a node name.
  3. Reach for the prebuilt. create_react_agent(llm, tools) replaces the hand-built ReAct loop. Drop down to hand-wired only when you need a non-standard variant.
  4. Distinguish "what's the graph?" from "what's in the node?" Reflection vs routing is a graph-shape choice. Which model the drafter uses, what the critic prompt says, what tools are bound — those are node-internal choices. They compose.

Session 21 adds interrupts and checkpointed memory on top of these. The graph stays the same; what changes is that you can now pause it mid-flight and let a human steer.

Glossary

Checkpointer
A pluggable state-persistence backend. MemorySaver (in-memory) for development; PostgresSaver for production. Required for interrupt() to work.
Conditional edge
An edge whose destination is decided at runtime by a small router function reading state. Wired with add_conditional_edges(source, router_fn, {label: dest_node, ...}).
create_react_agent
Prebuilt helper in langgraph.prebuilt that builds a compiled ReAct subgraph (agent ↔ tools loop) from an LLM and a list of tools.
Critic / LLM-as-judge
An LLM prompted to evaluate or critique another LLM's output rather than generate new content. Core to the reflection pattern and to evaluation pipelines.
interrupt(payload)
A LangGraph function called from inside a node that suspends graph execution and surfaces payload to the caller. Resumed via invoke(Command(resume=value), config=thread_config).
Multi-agent
A system in which two or more LLM-driven components with distinct roles collaborate through shared state. Different LLM calls in a row are not necessarily multi-agent; distinct roles are.
ReAct
Reason + Act (Yao et al. 2022). A loop pattern in which an LLM alternates between reasoning steps and tool calls until it produces a final answer.
Reflection pattern
Draft → critique → (optionally revise) → end. A graph shape for self-improving generation. Underlying research: Madaan et al. 2023, Self-Refine; Zheng et al. 2023, LLM-as-Judge.
Router function
A node-shaped callable that returns a literal string instead of a state update. Used by add_conditional_edges to pick the next node.
State
A TypedDict shared across every node in a graph. Nodes read from it and return partial dicts that LangGraph merges back in.
Thread ID
Unique identifier for one conversation/session in a checkpointed graph. Passed via config={"configurable": {"thread_id": "..."}}.
