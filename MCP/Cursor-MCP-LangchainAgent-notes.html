MCP · LECTURE 01 · STUDY NOTES

Agents, tools, and what MCP is for.

From @tool decorators to a Cursor wired up with 30 MCP servers — the consumer side of MCP.

AGENT = LLM + TOOLS + MEMORY + PLANNING MCP = USB-C OF LLM TOOLS
WHERE WE ARE

Prior sessions covered LangChain at a high level — prompts, chains, the basic LLM-as-function pattern. Today we add the missing pieces that turn an LLM into an agent: tools (the LLM can act on the world, not just generate text) and the management layer (MCP) that makes the tool catalogue scalable. Tomorrow's lecture flips this: instead of consuming third-party MCP servers, we'll write our own.

By the end of this session you'll know what an agent is, how to wire LangChain's @tool decorator to your own Python functions, why the LangChain-tools-in-a-list approach falls apart at scale, what MCP is and isn't, and what a Cursor configured with 30 MCP servers can actually do.

An agent is an LLM that can act on the world. LangChain's @tool decorator turns any Python function into something the model can call. That's fine for 5 tools, hopeless at 500. MCP is the USB-C of LLM tools — a standard wire format that lets any agent client plug into any tool server.
§ 01 — DEFINITION

What is an agent, precisely?

The lecturer's working definition:

Agent = LLM + tools + memory + planning

That matches the canonical Lilian Weng diagram from the 2023 OpenAI blog post "LLM Powered Autonomous Agents" — the picture you'll see on every agentic-AI slide deck for the next decade. Four boxes around a central LLM brain:

ComponentWhat it isWithout it
LLMThe language model itself — Claude, GPT-4, LlamaNo reasoning capacity
ToolsFunctions the LLM can call to act on the worldLLM can only generate text — no acting
MemoryPersistent state across turns (short-term, long-term, episodic, procedural)Every interaction starts cold
PlanningMulti-step reasoning, self-reflection, breakdown into sub-tasksLLM does one shot only

The act-not-just-talk distinction matters. A pure LLM can write you an email, draft a calendar invite, summarise a meeting — but it can't send the email, add the event to your calendar, upload the summary to Notion. Tools are what bridge that gap. Once an LLM has tools, it has hands. And once it has memory + planning on top, it has continuity.

SKILLS / HOOKS / SUBAGENTS

The lecturer mentions these as the planning layer in modern agent frameworks (Claude Code's skills, Cursor's hooks). They are not yet standardised across vendors. Skills are typically markdown files that describe procedures; hooks are event-driven triggers; subagents are spawned helpers. Treat these as evolving names for "the agent's instructions and orchestration."

JAVA/SPRING BRIDGE

An agent ≈ a Spring Boot app with autowired dependencies. The LLM is the core service; tools are the autowired beans (each one a function exposed for runtime invocation); memory is a persistent @Repository; planning is the orchestration class. None of them is novel architecturally — the novelty is that the caller is a probabilistic text generator rather than a deterministic program.

§ 02 — @TOOL

LangChain's @tool decorator

Any Python function becomes a tool by adding the @tool decorator from langchain_core.tools.

from langchain_core.tools import tool

@tool
def multiply(a: float, b: float) -> float:
    """Multiply two numbers together.

    Args:
        a: First number.
        b: Second number.

    Returns:
        The product a * b.
    """
    return a * b


@tool
def word_count(text: str) -> int:
    """Count the number of words in the given text."""
    return len(text.split())

Two things to internalise:

  1. The docstring is the description the LLM reads. The model decides which tool to call by reading docstrings. If your docstring is missing or vague, the LLM has no way to pick the right tool. Treat docstrings as user-facing API documentation, not optional annotation.
  2. Type hints matter. They become the JSON schema the LLM uses to know what arguments to pass.

The lecturer's slogan, paraphrased: "If you joined my team today and I gave you 10 functions with no docstrings, could you pick the right one for the task? No. The LLM is exactly the same."

Wrapping a third-party API as a tool

import os
from tavily import TavilyClient
from langchain_core.tools import tool

tavily = TavilyClient(api_key=os.environ["TAVILY_API_KEY"])

@tool
def web_search(query: str) -> str:
    """Search the web for recent facts or news using the Tavily Search API.

    Returns: a string containing the top results with URLs and descriptions.
    """
    result = tavily.search(query=query, max_results=3, include_answer=True)
    return str(result)
Correction — it's Tavily, not "Travely."

The transcript says "Travely Search" throughout. The product is Tavily (tavily.com), an LLM-focused search API. Free tier: 1,000 credits/month. The transcript error is an AssemblyAI hearing mistake.

Building the agent

from langchain.agents import create_tool_calling_agent, AgentExecutor
from langchain_openai import ChatOpenAI
from langchain_core.prompts import ChatPromptTemplate

tools = [multiply, word_count, web_search]
llm = ChatOpenAI(model="gpt-4o-mini")
prompt = ChatPromptTemplate.from_messages([
    ("system", "You are a helpful assistant. Use the tools provided when relevant."),
    ("placeholder", "{chat_history}"),
    ("human", "{input}"),
    ("placeholder", "{agent_scratchpad}"),
])

agent = create_tool_calling_agent(llm, tools, prompt)
executor = AgentExecutor(agent=agent, tools=tools, verbose=True)

result = executor.invoke({"input": "What is 12 times 11?"})

The model — given the user message, the tool list, and the docstrings — decides on its own that "multiply" is the right tool to call. No instruction "use the multiply tool" needed. That auto-discovery is the magic, and it depends entirely on docstrings being accurate.

Correction — when adding tools to the list, reference them, don't call them.

The lecturer's live demo errored with tool object is not callable. The fix: tools = [multiply, word_count, build_tavily_tool] — not tools = [multiply, word_count, build_tavily_tool()]. Decorated functions go in the list as references, not invocations. Common beginner gotcha.

§ 03 — SCALE PROBLEMS

Why naive tool lists fall apart at scale

The lecturer's industry example: her production system has ~3,000 tools (each SQL function that detects a specific kind of fraud or abuse is one tool). What goes wrong when you stuff 3,000 @tool-decorated functions into one agent's tools=[...] list?

Problem 1 — Context rot

Every tool's docstring is sent to the LLM as part of every prompt, so the model can decide which tool to call. With 3,000 tools at ~200 tokens of docstring each, that's 600,000 tokens — well over any model's context window. The model's "effective context" gets eaten by tool descriptions before the user even sends a message.

Context rot is the broader pathology: even when content fits in the context window, models pay less attention to information that's buried under unrelated tokens. Performance degrades long before the window fills up — Anthropic and others have measured this in needle-in-a-haystack benchmarks (Liu et al. 2023, Lost in the Middle).

Problem 2 — Tool ambiguity

Many tools in a large catalogue have similar descriptions. The lecturer's example: "paid amount per provider" and "paid amount per member" share 90% of their description text. The LLM picks the wrong one; you get a number that looks plausible but answers the wrong question. This is hallucination at the tool-selection level, not the text-generation level.

Problem 3 — Tool duplication across projects

Same tools — search, GitHub, Slack, Gmail, Postgres — get re-implemented by every team. In a 10,000-engineer org, the search tool might exist in 50 different codebases. Each version slightly different, none of them maintained in sync, all of them somebody's job to update when the API changes.

The fix: a protocol, not a library

What if tools lived outside the agent code, in dedicated processes (servers) that any agent (client) could connect to? That gives you:

  • One canonical implementation per tool (one GitHub server, used by everyone).
  • Servers grouped by domain (admin tools, devops tools, search tools, scraper tools — one server each).
  • Smaller per-conversation context (the client only loads the servers relevant to the current task).
  • Standardised wire format (any client can talk to any server, without per-pair integration code).

That's MCP.

§ 04 — DEFINITION

What MCP actually is

MCP (Model Context Protocol) is a JSON-RPC 2.0 protocol for exposing tools, resources, and prompts to LLM applications. Released by Anthropic on November 25, 2024. Adopted by OpenAI in March 2025 and Google DeepMind in April 2025 — making it the de facto industry standard.

What MCP is not:

  • Not an LLM. Not a tool itself. Not a framework.
  • Not an "intelligence boost" — it doesn't make models smarter.

What MCP is:

  • A standardised wire format for the conversation between an LLM application and a tool provider.
  • Three named primitives: tools, resources, prompts.
  • Two transports: stdio (local, server runs as a subprocess) and streamable HTTP (remote).
Correction — MCP runs at the application layer, not the TCP layer.

The lecturer said MCP is "a TCP layer protocol." Strictly, MCP is application-layer (layer 7 in the OSI model). It uses JSON-RPC 2.0 framed over either stdio pipes or HTTP — both of which sit above TCP. The distinction matters when you're debugging: if MCP isn't working, the TCP layer is almost never the problem; it's almost always the JSON-RPC framing or the tool/resource definition.

The architecture: host, client, server

  • Host — the user-facing application. One per session. Cursor, Claude Desktop, your custom IDE.
  • Client — a component inside the host that maintains a 1:1 connection to one server. A host with 30 configured MCP servers has 30 clients inside it.
  • Server — a process that exposes tools/resources/prompts.
Correction — Cursor is the host, not the client.

The transcript sometimes says "Cursor is a client." More precisely: Cursor is the host; inside Cursor live multiple clients, one per configured server. This matters because the host owns the LLM call, the user interface, and the session — it's the application; the clients are its connector subsystems.

JAVA/SPRING BRIDGE

MCP host ≈ a Spring Boot app with multiple RestTemplate beans. One application, many adapters underneath, each pointing at a different upstream service. Cursor is the Spring Boot app; each MCP client is a RestTemplate configured for a specific server.

The three primitives

MCP exposes three kinds of capabilities. They look similar in code but have different control semantics.

PrimitiveControlled byExampleCursor surface
ToolModel — the LLM decides when to callsearch_web(query)Invoked silently mid-conversation
ResourceApplication — the host attaches it to contextresource://docs/architecture.mdUser selects via @-mention or auto-attach
PromptUser — the user picks it explicitly/explain-topicSlash commands
Correction — "tools are auto-discoverable, resources are not" is the right shape but the wrong vocabulary.

All three primitives are listed via list_tools() / list_resources() / list_prompts(). The real distinction is who decides to call them: tools are model-controlled (LLM picks based on conversation), resources are app-controlled (host attaches based on UI), prompts are user-controlled (slash commands).

Correction — resources and prompts aren't "outdated" or "replaced by MLflow."

The lecturer prefers tools-only. They're not deprecated — Cursor uses prompts for slash commands; Claude Desktop uses resources for @-mention attachments. Skipping resources and prompts is a stylistic choice, not industry consensus.

§ 05 — DEMO

Using third-party MCP servers in Cursor

In Cursor (Settings → MCP), you add a server by pasting its config JSON. Once added, Cursor spawns a client for it; tools become available throughout the IDE. The lecturer's setup has roughly 30 servers configured — a sample of what's possible:

MCP ServerWhat it doesTools
GitHubPush, PR, issues, branches, search code22

FirecrawlWeb scraping at scale~6

Figma + 21st.dev Magic"Paste a Figma screenshot, get React components"~5
TwilioWhatsApp messages, SMSa handful
Postgres / BigQuery / many DBsSQL execution + schema introspection~10 each

That last column is the point. Cursor with MCP isn't a code editor any more — it's an agent that can act across your entire toolchain.

The flow in slow motion

When you type a request into Cursor with MCP servers configured:

  1. You type "Use search to find me LangChain's tool documentation."
  2. Cursor (host) sends the request + its full list of tools (across all servers) to the LLM.
  3. LLM picks a tool — tavily_search — and decides what arguments to pass.
  4. Cursor's client for Tavily sends a JSON-RPC tools/call to the Tavily server.
  5. Tavily server runs the actual tavily.search(...) API call against Tavily's backend.
  6. Result comes back as JSON to the client, into Cursor, into the LLM's context.
  7. LLM reads the result and either calls another tool or writes its final answer.

The model gets autonomous loop control — it can call as many tools as it needs, in any order, before settling on a final response. That loop is what makes the agent feel agentic.

Security caveat — not every MCP server is safe.

The lecturer's enterprise (a healthcare org) blocks almost all third-party MCP except GitHub. You should trust an MCP server roughly as much as you'd trust giving someone a shell on your laptop. Vetted servers from major vendors (GitHub, Anthropic, Cloudflare) are typically safe; randomly forked GitHub repos are not.

Correction — "LiteLLM is compromised, do not use" oversimplifies.

LiteLLM has had CVEs around its proxy server when the proxy is exposed to untrusted users. The LiteLLM SDK (used in-process by trusted code) is widely deployed in production. Read the CVE list, update to the patched version, and don't expose the proxy to untrusted users.

§ 06 — CATALOGUE

The catalogue: where to find MCP servers

By May 2026, the MCP ecosystem has several thousand servers. Browsing options:

  • modelcontextprotocol.io/servers — Anthropic's official catalogue.
  • GitHub modelcontextprotocol org — the source-of-truth repos.
  • mcp.composio.dev / mcp.so / smithery.ai — third-party indexes.
  • Awesome MCP Servers — the standard "awesome list" for the ecosystem.

Categories you'll encounter:

  • Version control: GitHub, GitLab, Bitbucket
  • Databases: Postgres, MySQL, MongoDB, BigQuery, Snowflake, Databricks, Neo4j, Qdrant, Pinecone
  • Search: Brave, Tavily, Exa, Perplexity, Kagi
  • Productivity: Notion, Linear, Jira, Slack, Discord, Gmail
  • Browsers: Playwright, Puppeteer, Stagehand
  • File systems / cloud storage: Google Drive, Dropbox, S3, local FS
  • Specialty: Figma, Stripe, Twilio, Spotify, etc.

If a product has an MCP server, the product is now agent-accessible. That's the single most important shift since the Transformer paper: every existing piece of software is becoming addressable by LLMs without per-product integration code.

§ 07 — IMPLICATIONS

Why this is the moment

The lecturer's macro point, paraphrased: what you do manually with a browser and a terminal — read docs, search, query a database, push code, file a ticket, fill a form — an LLM with MCP can now do, autonomously, with a single natural-language request.

The skills that make a developer most leveraged in 2026:

  1. Knowing what tools exist — being able to compose 5-10 MCP servers to solve a real problem
  2. Writing your own MCP servers for your domain (covered in Lecture 2)
  3. Designing the orchestration layer — when one agent isn't enough and you need a graph of cooperating agents (LangGraph, covered next)

Glossary

Agent
An LLM with access to tools, memory, and (optionally) planning. Distinguished from a pure LLM by its ability to act on the world.
@tool decorator (LangChain)
Marks a Python function as available to an LLM agent. The function's docstring becomes the LLM-visible description.
Context rot
Degradation of model attention and accuracy as context fills with mostly-irrelevant content.
Cursor
An AI-first code editor (cursor.com). Built-in MCP host since 2025.
Host (MCP host)
The user-facing application. Owns the LLM calls and the UI.
JSON-RPC 2.0
The wire format MCP uses. Application-layer (layer 7) protocol, transport-agnostic.
MCP (Model Context Protocol)
Anthropic's protocol for connecting LLM applications to tool providers. Released November 2024.
MCP Client
A component inside a host that maintains one connection to one server.
MCP Server
A process that exposes tools, resources, and prompts via the MCP protocol.
Prompt (MCP primitive)
A reusable templated instruction the user invokes. User-controlled.
Resource (MCP primitive)
Read-only content (files, configs, documents). Application-controlled.
stdio transport
One of MCP's two transports. Server spawned as a subprocess; communication via stdin/stdout pipes.
Streamable HTTP transport
MCP's networked transport (replaced the older HTTP+SSE in the 2025-03-26 spec).
Tavily
A search API designed for LLM agents (tavily.com). Free tier of 1,000 credits/month.
Tool (MCP primitive)
A callable function the LLM can invoke. Model-controlled.
